# ITD 25 — One Page, One Set of Figures, One Row

| ITD 25 — *"Use three server components — `Page`, `FigureGrid`, `CommitmentRow` — to render the page shell, the three figures and a commitment in a list, so that eight routes cannot drift apart again."* |  |
| :---- | :---- |
| **THE PROBLEM** | The product agrees with itself about *what* to show and disagrees with itself about *how*. The page shell — `.page`, a back link, `.page-header` with an eyebrow, an `h1` and a lede — is copy-pasted into `page`, `shop`, `product` (six branches), `consent`, `bill`, `read`, `account` and `receipt`, so the back-link wording was decided per file: *Back to the ways in* on four screens, *Back to the search* on five, *Back to this product* on one, and none at all on the account page. <br><br> The three figures are worse: `CommitmentView` renders them as `.commitment-figure`, `CommitmentRecord` hand-rolls a grid whose first tile is *Next charge* so the record opens on a figure that is not one of the three, and `/account` renders a third `.account-figure`. Same data, three visual languages, and the account rows show figures with no way to open the record they summarise. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Three primitives: `Page` (eyebrow, title, lede, back, children) owns `.page` and the header rhythm; `FigureGrid` renders the three figures at `full` or `compact`; `CommitmentRow` renders one commitment in a list, with its status and a link to its record.** <br> 2. Do nothing structural and fix the copy inconsistencies by hand. <br> 3. A full design system with a component per element. <br> 4. One `Figures` component with props that make it render any of the three layouts. |
| **REASONING** | The drift has one cause: each screen owned its own copy of the same decision. Fixing the wording without removing the copies fixes today and not next week, and there are still screens to be built. Option 1 removes the copy, and it does so at the smallest unit that actually repeats — a page frame, a figure set, a row — rather than at the level of a design system, which this product does not have and does not need for eight routes. <br><br> `Page` also decides something the routes have each decided badly: **the back link is not optional**. A destination that navigates itself is the frame's job (IPD 28), but a screen reached by drilling into something — a product, a bill, a consent, a record — needs a way back to where it was reached from, named after the thing rather than after a metaphor. *Back to the ways in* is a phrase used nowhere else in the product; `back` takes a label so the route names its own parent in the product's own vocabulary. <br><br> Keeping *Next charge* out of the figure set is the second decision inside this one. The three figures are the product: across the term, cost to leave, charged today. *Next charge* is a fact about the agreement, not a fourth figure, and putting it first on the record made the one screen a shopper keeps open on the wrong number. It moves to the record's standing line, beside the status, where the date already lived. <br><br> Option 4 is rejected because a single component with a layout prop becomes a switch on three shapes, and the record's need (a quotation under a figure, a cancel button inside it) is not the shop's need. Two variants of one grid is the honest amount of variation; three bespoke renderers was not. |
| **TRADEOFFS** | Three more files to read before a screen makes sense, and a change to the figure set now goes through one component that eight screens depend on — which is the point, and also the blast radius. <br><br> `Page` cannot know whether a route's back target is right; it only guarantees one exists and is labelled. A route can still name the wrong parent, and only review catches that. <br><br> The receipt's figure grid loses its leading *Next charge* tile and gains a line; the spoken version already listed the three figures and the next charge separately, so the screen and what it reads aloud now agree. |
| **NOTES** | The server computes every figure before the component sees it (ITD 17); the primitives render and never derive. `FigureGrid`'s `compact` variant is the account row's: label, amount, arithmetic, no quotation — a row that carried the seller's sentence would be a page. |
