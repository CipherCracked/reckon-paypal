# ITD 18 — Reading a Seller's Published Terms

**Status:** Implemented (2026-11-08)
**Date:** 2026-11-08
**Answers:** Problem tree Q3 of `../intro.md`, the technical half — *how does a seller's prose become an exit figure?*
**Serves:** IPD 19 (silence is reported, prose is read) and inherits ITD 12 (`../../universal-commitment-companion/itds/quote-grounded-reading.md`) unchanged.

| *"Reuse the quotation pipeline on the seller's own words: the model copies spans, the server verifies them, and the parser turns a verified span into an amount."* |  |
| :---- | :---- |
| **THE PROBLEM** | IPD 19 decides the exit figure comes from the seller's published words, because PayPal has no field for it. The build already turns prose into figures in one place: `lib/ai/read-document.ts` → `lib/document/parse.ts` → `lib/commitment/compute.ts`. Its tool schema has **no numeric field** — the model may only copy spans, the server drops any span not literally present in the pasted text, and the parser extracts amount, count, cadence and date from the surviving span. That pipeline has run live (6 quotations, 0 rejected). What it has never been pointed at is a source the product fetched rather than one the shopper pasted: a catalogue entry's description, or an invoice's `detail.terms_and_conditions`. The question is whether that is a reuse or a second reader. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Reuse the pipeline as-is; only the fetch changes. The source text is a catalogue description or an invoice's terms field instead of a pasted document, and every other stage — tool schema, span verification, parse, compute — is unchanged.**<br>2. Ask the model for the exit amount directly, with a schema field for it.<br>3. Run the existing pattern-based `candidates` scan over the seller's text and show the amounts it finds, uninterpreted.<br>4. Read the exit figure only from structured fields and never from prose. |
| **REASONING** | Option 2 is the design ITD 12 exists to prevent. A model that returns a number is unverifiable by construction: there is nothing to check it against, so the screen's claim becomes "the model said so", which is exactly the provenance problem this tree was opened to fix. Option 3 is already built and is the honest fallback when reading fails — it finds amounts by pattern and labels them uninterpreted — but it cannot tell an exit fee from a deposit, so it cannot produce a figure on the third line. Option 4 would leave the exit line empty on every text-only source, including every invoice whose seller wrote their policy in `terms_and_conditions`, which is the only structured-enough field PayPal offers. Option 1 costs almost nothing: the tool schema, the verification loop, the parser and the guard already exist and are tested, and the change is which string is handed to the reader. The one thing that is genuinely new is the *refusal*: the model must be able to answer "this text states no cancellation policy", and that answer must arrive as a finding rather than as an error, because on this source silence is the expected answer most of the time. |
| **TRADEOFFS** | A model call sits between the shopper and the third figure, so a failed read must degrade to "Not stated — the seller's terms could not be read", never to zero and never to a candidate amount dressed as a figure. The source text is short (a product description is two sentences; `terms_and_conditions` is a field), so the pipeline's tolerance for long documents is not exercised here. Reuse means the reader's quirks are the exit figure's quirks: the parser refuses two amounts in one span, which on a product description containing a price and a fee will produce an absence rather than a guess. |
| **NOTES** | The existing error taxonomy already separates the cases and must not be flattened: `ModelError` (no usable answer) is not `UnreadableDocumentError` (answered, nothing readable), and neither is an absence. An absent exit figure carries a reason via `figureNotes` today; that mechanism is what renders the difference between "the seller published nothing" and "we could not read what the seller published". Reuse also means the same rule holds here that holds on `/read`: a figure from prose keeps the sentence that produced it, and that sentence is what the provenance line refers to (IPD 18). **Built 2026-11-08:** `requestQuotations` in `lib/ai/read-document.ts` exposes the spans without the rule that zero spans is a failure; `readDocumentWithModel` keeps that rule for the paste path by wrapping it. `lib/document/verify.ts` holds the span check both readers call, lifted out of `app/api/read/route.ts` unchanged. `lib/commitment/published-exit.ts` turns verified `exitFee` / `freeToLeave` spans into an `ExitTerms` and reports `silent` and `unreadable` separately. The parser's two-amount refusal was kept as written, which turns an ambiguous cancellation sentence into an absence rather than a choice. The invoice's `terms_and_conditions` is **not** wired: the bill page reads the biller's description, and reading the invoice's own free-text field needs a live invoice object to test against. |
