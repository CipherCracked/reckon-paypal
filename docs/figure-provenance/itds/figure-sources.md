# ITD 17 — Figure Sources

**Status:** Implementing (2026-11-08) — the plan path is built and wired to the consent route; the shop sources nothing yet
**Date:** 2026-11-08
**Answers:** Problem tree Q1 of `../intro.md` — *which figures must come from PayPal, and which may it never supply?*
**Serves:** IPD 18, which can only write a provenance line once each figure has a named source.

| *"Read each figure from the object that can prove it, and record which object that was."* |  |
| :---- | :---- |
| **THE PROBLEM** | All three figures are computed in one place, from one file. `app/api/commitment/[orderId]/route.ts:18` calls `computeCommitment(product.terms)` where `product` came from `findProduct(slug)` — a literal in `lib/catalog/products.ts`. The route takes an `orderId` and never uses it. The only PayPal read behind any money screen is the invoice amount in `retrieveInvoice`, and it is used for a disagreement check, not as a source. So the architecture has no concept of where a figure came from, which is why the screen was free to claim the order. Compounding this, the three figures are not one kind of thing: what is charged today is a fact about a transaction, what it adds up to is arithmetic over a plan, and what it costs to leave is a policy no PayPal object holds. No single object can answer all three. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Each figure declares the PayPal object it was read from; our arithmetic turns that object's numbers into the figure; where no object exists, the figure is computed from the seller's published terms and declares those instead.**<br>2. One authoritative object per screen, read once — use the order for every figure on a purchase screen.<br>3. No PayPal source at all; compute everything from the catalogue, and say that.<br>4. Fetch a PayPal object per figure at render time. |
| **REASONING** | The mapping is fixed by what each API models. An **order** carries `purchase_units[].amount.value` and `amount.breakdown` (`item_total`, `shipping`, `tax_total`) — what is charged, and what it is made of. A **billing plan** carries `billing_cycles[]` (`frequency`, `total_cycles`) and `pricing_scheme.fixed_price`, plus `payment_preferences.setup_fee` — the term, the per-cycle price and a one-off charge. An **invoice** carries `items[].unit_amount`, `detail.due_date` and `detail.invoicer` — a bill's amount, its deadline and who sent it. A **catalog product** carries a name, a description, a type, a category and an image, and **no price at all**, which is why a shop listing built from PayPal needs a plan read per product. Because the three figures answer three different questions, option 2 is not merely inconvenient — an order has no term, so a purchase screen built on option 2 cannot show the term total, and a plan has no tax, so a subscription screen built on it cannot show what is charged. Option 4 puts three round-trips in front of the first paint, and for two of the four doors there is no object to fetch yet. Option 3 is the state being corrected. The decision is therefore less about picking an object and more about defining a claim precisely enough to test: **a figure is derived from PayPal when our code computed it, in the same request, from numbers read from a named PayPal object, and the object's id is returned alongside the figures.** Anything else is computed from published terms and must say so. That definition is what makes the provenance line in IPD 18 checkable rather than rhetorical. |
| **TRADEOFFS** | Every figure now carries a source, so every component between the route and the `<dd>` must thread it — the figures array stops being a list of numbers and becomes a list of claims. The consent path gains a second round-trip it does not make today, because a subscription's term lives on a plan and not on the order. Recording an object id is not persisting it: nothing is stored (IPD 8), so a figure cannot be re-proved after the response has been sent. |
| **NOTES** | Failure states are part of this decision, not an afterthought. **PayPal unreachable** — the figures are computed from the seller's published terms, labelled as such, and the existing notice stays; the screen still works. **PayPal returns an amount that disagrees with the terms** — no total is shown, which the bill page already does. **Empty catalogue** — the entry still works, because the entry computes locally and creates nothing. Invoice `detail.terms_and_conditions` and `detail.note` are merchant free text and are the only structured-enough place a seller can publish an exit policy (ITD 18). **Built 2026-11-08:** `lib/paypal/catalog.ts` (`minorFromPayPal`, `termsFromPlan`, `readProductFromPayPal`) and `GET /api/commitment/{orderId}` now resolves PayPal first and returns `sources` in the payload, so the screen cannot name a source the route did not read. The product id for each slug comes from `PAYPAL_PRODUCT_*` in the environment; unset is the normal state and means the published terms are used. A plan with no fixed price, no readable interval, or unlimited cycles yields **no terms at all** rather than an approximation. Unverified against a live sandbox — credentials are still failing — so the mapping is tested against fixture payloads only. |
