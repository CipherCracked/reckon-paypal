# ITD 14 — Return Paths

**Status:** Adopted (2026-11-07) — not yet built
**Date:** 2026-11-07
**Answers:** Problem tree Q4 of `../intro.md`.
**Serves:** IPD 15 (one canonical path; a cancelled return lands on the commitment; the record is the end).

| *"Use the URL as the only state, with an explicit back target per screen, so the journey survives an external redirect and back never re-triggers a payment."* |  |
| :---- | :---- |
| **THE PROBLEM** | The canonical journey leaves the app for PayPal and returns to a fresh document (`/consent/pending?approved=1&token=…`). In-memory state does not survive that redirect; browser history does not either, in any way the app can trust. The screen must nonetheless know which order it is talking about, must capture exactly once on return, and must offer a back action that does not land on the pre-approval screen or on PayPal. The same route also serves a cancellation (`?cancelled=1`) and a visit with no order at all (`/consent/pending?slug=…`), so "where am I in the journey" has to be answerable from a URL that carries three different situations. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **The URL is the only state: `/consent/pending?slug=…` before payment; PayPal returns to `?approved=1&token=…`; the token is treated as the order id; every screen declares its own back target; no history manipulation; capture is guarded by a ref and idempotent on the server.**<br>2. A client state machine with `history.pushState` guards that rewrite the URL per step.<br>3. Store the in-progress commitment in `sessionStorage` and restore it on return.<br>4. Keep the shopper inside the app by embedding PayPal's approval (not available without the PayPal client script, which the product does not load). |
| **REASONING** | The external redirect creates a new document, so anything held in memory is gone and anything written to history is gone with it; the URL is the only thing PayPal carries back. Making the returned `token` the order id means the returned screen is about a real PayPal object without the app storing anything, which is the same principle the receipt already runs on. Capture already tolerates repetition — a second capture answers `ALREADY_CAPTURED` — and the client already guards with a ref; both must stay, because a back-then-forward through the browser can replay the effect. Option 2 adds history entries the user did not ask for and breaks under the external redirect anyway. Option 3 is a store of a commitment about a person, which IPD 4 rules out for the sake of a convenience the URL already provides. |
| **TRADEOFFS** | Order ids appear in the URL and are guessable payment references — accepted already in ITD 6, because no name, address or account travels with them. Closing the tab loses the in-progress commitment, because nothing is stored; the shopper starts again from the entry. The token-as-order-id convention depends on PayPal's redirect contract, so it needs a test that fails if the parameter name changes. |
| **NOTES** | The cancel path (`?cancelled=1`) returns to the commitment with a statement that nothing was charged; its back target is the product, not PayPal. Back from a returned, captured payment goes to the record, not to the consent screen, so the shopper cannot re-enter the payment state. The receipt route stays read-only and is never a back target for a payment in progress. |
