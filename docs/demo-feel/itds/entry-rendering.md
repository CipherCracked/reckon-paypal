# ITD 16 — Entry Rendering

**Status:** Adopted (2026-11-07) — not yet built
**Date:** 2026-11-07
**Answers:** Problem tree Q3 of `../intro.md` — *what must the first screen establish before anyone clicks?*
**Serves:** IPD 14 (one commitment worked in full, before any interaction, with no model key).

| *"Use server-side computation of the entry from the catalogue, with no model key and no PayPal call, so the first paint already shows a worked commitment and nothing is created by a visit."* |  |
| :---- | :---- |
| **THE PROBLEM** | The entry has to show one commitment worked in full before any interaction (IPD 14), for a judge whose first screenshot may be the only version of the product they see, and for a shopper on a slow phone. The figures must be real, must not depend on a model key being configured, and must not cause anything to exist at PayPal: an abandoned visit must leave no half-made order or invoice. The current home computes one figure per door on the server already, so the mechanism exists — what is undecided is where the worked example's facts come from and what is allowed to happen while rendering it. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **The entry is a server component over the catalogue: `computeCommitment` and `presentFigures` run at request time for the worked example, with no AI call and no PayPal call; PayPal objects are created only when the shopper acts.**<br>2. The entry renders a shell and fetches the commitment from `/api/commitment` on mount.<br>3. The worked example is computed at build time and frozen into static HTML.<br>4. A real invoice or order is created when the page loads, so the figures are live PayPal amounts. |
| **REASONING** | The figures are deterministic and cheap, so the server can produce them and the first paint is complete without JavaScript, without a key, and without a network round trip after load. The model only supplies wording, and its absence already degrades honestly, so the entry must not wait for it. Option 2 delays the only thing the screen exists to show and makes the first screenshot depend on a client render; for a judge viewing a static capture, the figures may not be there at all. Option 3 freezes the catalogue into the build, which breaks the drift test's premise — the document is meant to prove the code, and stale HTML proves nothing. Option 4 is the one that must be refused explicitly: rendering a page is not consent, and creating a PayPal object on load would litter the sandbox and make an abandoned visit leave a half-made bill. |
| **TRADEOFFS** | The entry renders per request rather than as static HTML, which costs a little latency for a page whose content barely changes. The worked example's facts come from catalogue terms, not from a PayPal object, so the entry cannot claim the stronger attribution the consent screen eventually can — and must say where its numbers came from, which is also the correction of the attribution defect the audit recorded. |
| **NOTES** | The entry's source line reads *computed from the terms shown*; the consent screen's attribution is decided separately, once a real order exists. The same rule covers the bill door: pressing it is what creates the invoice, and nothing is created before that. Degraded wording (no model key) changes only the summary and labels, never the figures — the existing degraded path already works this way and is unchanged. |
