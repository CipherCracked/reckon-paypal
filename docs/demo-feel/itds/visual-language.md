# ITD 15 — Visual Language

**Status:** Adopted (2026-11-07) — not yet built; no utility framework, by explicit decision
**Date:** 2026-11-07
**Answers:** Problem tree Q5 of `../intro.md` — *what must survive the restructure?*
**Serves:** IPD 17 (one rendering, nothing in the frame that adapts), IPD 14 (a first screen that reads as a product).

| *"Use design tokens on `:root` with a modular type scale, semantic surfaces and a `prefers-color-scheme` theme, to make one visual language across eight routes without a framework."* |  |
| :---- | :---- |
| **THE PROBLEM** | The product's whole visual system is one 436-line stylesheet with a flat palette, ad-hoc font sizes, one radius and no dark theme. Eight routes were styled as they were built, so the coherence a judge reads as "product" is carried by consistency the code does not enforce. There is no designer and five days, so whatever mechanism is chosen has to make consistency checkable rather than remembered. The system also has to accommodate the reader-owned text-size control (IPD 10) without fighting it. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Tokens on `:root` — colour, space, type scale, radius, focus — with three semantic surfaces (page, raised, muted), one accent, a modular type scale, and a dark theme via `prefers-color-scheme`. No imagery inside the decision area.**<br>2. A utility framework (Tailwind) with its own scale and configuration.<br>3. A component library (shadcn/ui or equivalent) for buttons, cards and layout.<br>4. Keep the single stylesheet and restyle each route by hand. |
| **REASONING** | Eight routes and one hand: tokens are the smallest mechanism that turns "look consistent" into "uses the same value", and they are a change to one file rather than a new dependency. A utility framework brings a vocabulary and a build step to a codebase that already has components, and its return comes from repetition across many screens; at eight routes with one hand, the token file *is* that vocabulary, and adopting a framework to avoid writing one stylesheet trades a dependency for a few hundred lines. A component library brings opinions about markup that would have to be rewritten to meet the accessibility decisions already recorded (landmarks, figure ordering, no modes). A modular scale removes the ad-hoc sizes that make two routes read as two documents. Dark mode is a second block of tokens, and a 2026 product is expected to answer the system setting; the cost is checking contrast twice, which the tokens make mechanical. |
| **TRADEOFFS** | The token pass touches every rule, which is a day of visual regression risk across routes that are currently correct. Two themes double the contrast-checking surface. Removing imagery leaves the shop sparse, and sparseness is exactly what the first tree was told to avoid — type, spacing and one accent have to carry the hierarchy instead. |
| **NOTES** | Contrast is checked against WCAG 2.2 AA in both themes, including the focus ring, which has its own token. No meaning is carried by colour alone (the figures, the "Not stated" state and any notice already carry text). The reader-owned text scale multiplies the token scale rather than replacing it, so a reader who enlarges text does not lose the hierarchy. No stock photography anywhere: decorative imagery, if used at all, is `aria-hidden` and never beside a figure (IPD 17).
The utility framework was considered and set aside explicitly on 2026-11-07: the app is eight routes, the build works today, and the tokens reach the same result without a dependency or a build step. Revisit only if the surface grows past what one stylesheet can hold. |
