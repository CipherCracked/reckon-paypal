# Accessible Commerce Companion — ITDs

| ITD 2 — *"Use deterministic code for every figure and the model only for language and extraction."* |  |
| :---- | :---- |
| **THE PROBLEM** | The product turns merchant copy and order data into language a shopper can judge. Arithmetic cannot be delegated to a language model: one wrong total ends the product's usefulness, and models produce confident wrong numbers. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Code computes all monetary values; the model reads product text and terms, labels charges, and drafts the restatement.**<br>2. The model performs the arithmetic as well.<br>3. Rules and templates only, with no model.<br>4. The model with a calculator tool. |
| **REASONING** | The split follows the failure mode. Arithmetic has a verifiable answer, so it belongs in code where it can be tested. Language has no single answer and varies per merchant, so it belongs to the model. Option 2 breaks the core promise. Option 3 cannot read the range of merchant copy a real checkout carries. Option 4 still leaves the model choosing which numbers matter, so a wrong mapping remains possible. |
| **TRADEOFFS** | Two components to coordinate, and model output must be constrained so it never states a figure the code did not produce. The response contract needs guarding. |
| **NOTES** | Model choice is deferred; the binding constraint is a structured contract where monetary values are supplied to the model, never generated by it. |

---

**Revision — 2026-11-07: what was actually built, and what the AI is still not doing.**

**Resolved.** The model is `claude-sonnet-5-5`, called with a **forced tool** whose input schema
contains no monetary field at all — not an amount, not a price, not a total. The model returns three
item labels and one plain-language summary. Its output is then passed through a guard that rejects
any figure-shaped string (`MoneyInModelOutputError`) before it reaches the page. The binding
constraint stated in the Notes is therefore enforced twice: once by the schema, once by the guard.

**Verified behaviour.** When the model is unavailable — no key, network failure, rejected output —
the route returns the same translation with fallback labels and `degraded: true`. Every figure
survives; only the wording is lost. This is the "position of last resort" the reasoning calls for,
and it is tested.

**Still open, and this is the honest gap.** The model currently does *one* thing: it writes a
sentence and labels three line items. That is genuine but thin use of AI for a product whose subject
is comprehension. IPD 3's revision reframes the rendering as a hypothesis, and the model's part in
it is the natural next extension — reading merchant language the catalog cannot anticipate (jargon,
fine print, unusual terms) rather than rewording a description we wrote ourselves. Nothing about the
guard changes if that happens: more of the model's work moves into language, and none of it into
money.

**Note for the demo.** With no key configured, the shipped app runs the degraded path on every
screen. The AI half of the product is invisible until a key exists, which is a demonstration problem
before it is an engineering one.

**Revision — 2026-11-07 (2): the model's job, now that the rendering is a hypothesis.**

IPD 7 took the model out of presentation entirely — the ordering, the unit and the arithmetic are
templated from computed data — and named the work it should be doing instead: **reading merchant
language the catalogue cannot anticipate.** That changes what this ITD's decision means in practice.

**The extraction the product actually needs** is not three labels. It is the terms the computation
consumes, taken from prose: does this commitment repeat, how many times, over what period; is there an
exit fee, and what does the seller say about cancelling; is a term genuinely absent or merely buried.
The shipped catalogue supplies all of this by hand — `{ kind: "unknown" }` for the mattress is a
human having decided the page says nothing — which is exactly the judgement a real deployment cannot
make in advance.

**Revision — 2026-11-10: the hand is now a curated map with a verified quote.** The mattress entry is
deleted, and recurring products come from live Channel3 listings. The facts a listing does not carry
(a cadence and a term length) live in `lib/market/subscriptions.ts` as `{ count, period, quote }`,
where the quote must appear verbatim in that listing's title or description. The quote is checked
against the record on every resolution: a merchant who rewrites the sentence removes the term rather
than being quoted from memory. That is narrower than a model reading prose, and deliberately so — it
is the smallest honest bridge between a feed of words and terms the arithmetic can consume. The exit
figure is still read from the merchant's description at request time, and its silence is still
reported as **Not stated**.

**The risk this introduces, stated plainly.** A model that reads a fee out of prose can read it
wrongly, and unlike a label, a wrong term produces a wrong figure downstream — the guard cannot catch
it, because the guard only inspects output, and the number was computed afterwards by code that
trusted the input. Two mitigations belong with any move in this direction, and neither is optional:

1. **Every extracted term carries the merchant's own span**, shown to the shopper beside the figure it
   produced. A misreading then becomes visible and attributable rather than silently authoritative.
2. **The drift guard keeps its authority over the total actually charged**, so a misread still cannot
   survive a disagreement with PayPal.

**What does not change.** The model still never emits a figure. Its schema still contains no monetary
field, and the guard still runs on whatever it returns. Moving work into extraction moves it toward
the numbers, which is why the two mitigations above are the price of the move rather than a
refinement of it.

**Honest status.** None of this is built. The extraction stays hand-performed in the catalogue, and
the app therefore does the right thing with terms it was given and nothing with terms it was not.

**Revision — 2026-11-07 (3): the transport is a contract, not a vendor.**

The question this revision answers is not *which model* but *what we speak*. A hackathon entry that
hard-codes one provider's endpoint and one provider's headers is a demo that only runs on the
author's machine; the product's claim — that any seller's commitment can be translated — implies
the model underneath is replaceable.

**What the ecosystem actually settled on.** The OpenAI chat-completions shape with function calling
is the de facto interchange format for models. The evidence is one-directional and unambiguous:

- **LiteLLM**, the reference open-source gateway, exists to accept one format for 100+ providers
  and translates every backend into it — and offers a proxy that serves that same shape.
- **Amazon Bedrock** exposes `POST /v1/chat/completions` alongside its native API.
- **Google's Gemini API** ships an OpenAI-compatibility endpoint.
- **Anthropic** ships an OpenAI SDK compatibility layer, so even the vendor whose native shape is
  `/v1/messages` speaks the other one.

The reverse does not hold: there is no Anthropic-Messages-compatibility layer at OpenAI, Google or
Bedrock. Chat completions is therefore the strictly wider contract, and the SDK question is
secondary — a vendor SDK is a fine *contract*, but it is one more thing to swap when the provider
changes. What was wrong in the first draft was neither: it was **provider-shaped code** — a
gateway's session header and its base-URL quirks written into the request path.

**Decision.** One file (`lib/ai/client.ts`) speaks `POST {AI_BASE_URL}/chat/completions` with a
forced function call, using `fetch`. The endpoint, the model id and the key come from `AI_BASE_URL`,
`AI_MODEL` and `AI_API_KEY`. No vendor package, no vendor header, no provider branch anywhere.
A provider that does not serve that shape is reached through a proxy in front of it, which is the
ordinary deployment pattern rather than an integration we write.

**What we deliberately do not rely on.** The compat layer Anthropic documents ignores the `strict`
parameter, so a schema-conformant answer is not guaranteed by the wire. That is not a problem this
design has to solve: conformance is re-established on our side — quotations are checked to be
literal substrings of the document, fields are checked against a closed list, and a figure in the
prose summary is discarded. The transport may be lax; the reader is not.

**Rejected.** The Anthropic Messages shape (a good contract, a narrower surface — see above). A
framework with a provider registry, and an in-process gateway: both are real options that buy
provider coverage we already have for free, at the cost of a dependency and an abstraction to debug
inside a five-day build. Documented here so the choice is a decision rather than an omission.

**Revision — 2026-11-07 (4): the transport belongs to the reference client, not to us.**

Revision (3) said the SDK question was secondary and shipped raw `fetch`. That was the wrong call
on a smaller point. The reasoning rested on a false premise: that a request is the only thing an
SDK adds. It adds the things that are *not* in the request — retrying 408, 409, 429 and 5xx with
exponential backoff that honours `Retry-After`, a timeout that actually fires, and an error
taxonomy that separates "slow down" from "the model does not exist".

Hand-written code has none of that, and cannot get it without becoming the thing it was avoiding.
Worse, the compatibility literature we read for this revision is uniform on one practice: the way a
server's OpenAI compatibility is *tested* is by running the official client against it, because
"compatible" means "works with the reference client". Writing our own transport means we are the
only party to our own definition.

**What changed.** `openai` is now the one runtime dependency besides Next and React.
`lib/ai/client.ts` still owns the configuration, the forced tool choice, the "no provider
configured" case and the refusal of prose; it no longer owns sockets, backoff or status parsing.
The callers and the guards are untouched — which is the point of the seam, and how this revision
could be a twenty-line change rather than a rewrite.

**What has not been delegated, and will not be.** No SDK or framework supplies this product's actual
invariant: that a quotation is a literal substring of the document, that fields come from a closed
list, that a figure in prose is discarded, that nothing is computed from an unverified span. The
closest framework feature — schema-constrained object generation — *trusts* the schema, and the
compatibility record says why that is not enough: Anthropic's layer ignores `strict`, Ollama ignores
`tool_choice`, and a non-conforming answer can arrive with HTTP 200. The transport can be borrowed.
The verification cannot.

**Revision — 2026-11-07 (5): frameworks and gateways, examined and declined.**

Both were surveyed on their own terms — AI SDK, LangChain/LangGraph, LlamaIndex and the Agents SDK
as frameworks; LiteLLM, OpenRouter, Portkey and the hosted AI gateways as gateways. Neither is a bad
tool. Both are the wrong tool here, for reasons specific to this product rather than to taste.

**Frameworks are built for shapes we do not have.** Their value concentrates in streaming token
output, chat UI hooks, agent loops, tool orchestration and retrieval. This app has none of them: it
makes one non-streaming call per page, asks for one tool, and renders the result. What a framework
would add on top of the reference client is a provider registry — which for us is `AI_BASE_URL`,
`AI_MODEL` and `AI_API_KEY`.

**And their abstraction leaks where this product cannot afford it.** Documented cases exist of a
provider package silently discarding provider options, and of cross-provider fallback shipping as a
separate dependency rather than a feature. In a chat app that is an inconvenience. Here it is the
worst available failure: if a silently dropped `tool_choice` turns into prose, the reader degrades
to candidate mode and looks *exactly* like a document that could not be read. The one distinction
the product exists to make would be lost inside a dependency. Our tests assert the request itself —
that is a safety property, not a convenience, and a framework would turn the assertion into "trust
the framework".

**Gateways solve a problem of scale, and we have one service.** The gateway literature is unusually
consistent about the threshold: central enforcement, routing, fallbacks, spend tracking and
per-request observability become the better default once *more than one service* calls a model. One
Next app calling one endpoint is below it. Self-hosting LiteLLM adds a second deployable and a new
way for the demo to fail on the day; putting OpenRouter in the middle adds a vendor account between
the shopper and the model. Both remain available as **escape hatches rather than architecture**: if
a chosen provider does not speak the format, `AI_BASE_URL` points at a gateway and nothing else
changes. That is the cheapest possible way to keep the option.

**What would change the answer.** A chat surface with streaming, a model chosen at runtime for cost
or capability, more than one service calling out, or a need to attribute spend per user. Any of
those and the AI SDK or a gateway starts paying for itself. The trigger is written down so the
decision can be revisited on evidence rather than re-argued.

**Revision — 2026-11-10 (6): thinking is a setting, and off unless asked for.**

A reading was taking **123.6 s** and timing out a 60 s budget. The diagnosis was not the endpoint,
the key or the schema. Measured on the app's own request: the model streamed its first token in
**1.7 s** and then spent **4,941 reasoning tokens** producing a **122-token** answer — 95% of its
output was private thinking, and the total was **68.6 s**. A non-reasoning model on the identical
request: first token 1.2 s, **3.1 s** total, **zero** reasoning tokens.

**The latency figure in a provider's marketing is time to first token.** It was not a lie; it was
not the number that decides whether a page renders. And a reasoning model's thinking gives a
non-streaming caller nothing until it is finished — this app does not stream, so a fast first token
is invisible to it. That is the whole failure: an answer that began immediately arrived too late.

**The decision.** `AI_REASONING_EFFORT` names how much the model may think. **Unset means `none`** —
thinking is off unless someone asks for it. `none` sends `{ "enabled": false }`; a graded value
sends `{ "effort": "<value>" }`; `default` sends no such field at all, which is the neutral request
the format defines.

**Why the default is `none` and not silence.** The failure this setting exists to prevent is not
hypothetical: a reading took 123.6 s against a 60 s budget and every page fell back, while the
error on screen said the endpoint could not be reached. A default that leaves the decision to the
provider leaves that failure available to every deployment that never heard of the variable. Since
the job is copying, `none` costs nothing this product claims — so the safe state is the default one
and the escalated one is opt-in.

**The price of that default, named rather than hidden.** `reasoning` is *not* part of the
chat-completions schema — it is a gateway extension, the same class of thing revision (4) removed
when it dropped a gateway's session header. Sending it by default means the ordinary request is no
longer the one the format defines, and an endpoint that **rejects** unknown body fields, rather
than ignoring them, would now fail where it previously worked. That is a real trade and it was
taken deliberately: the failure it prevents is one that actually happened here, twice, and the one
it risks is hypothetical and **one environment variable away** — `AI_REASONING_EFFORT=default`
omits the field entirely and restores the neutral request. The escape hatch is the reason the trade
is acceptable; without it, this default would have been wrong.

**The hazard, measured rather than assumed.** A graded effort is a *request*, not an instruction.
Against one free model, `effort: "low"` was accepted, charged, and **silently ignored** — the model
still spent 1,183 reasoning tokens and took 20 s. `none` was honoured (0 tokens, 2.5 s). So the
only value this setting can be *claimed* to deliver is `none`; the graded ones are best effort of a
third party, and a deployment that needs a guarantee should choose a model that does not reason
rather than one whose reasoning it hopes to dial down.

**An unrecognised value is an error, not silence.** A typo in a setting that only makes things
faster would otherwise be indistinguishable from a slow model: full-length thinking, a page timeout,
and nothing on screen connecting the two. `aiReasoningEffort()` therefore throws, naming the values
it accepts, before any request is sent.

**Why this is acceptable here and would not be for everyone.** Reading a document is *copying*: the
system prompt says never to compute, the schema has no monetary field, and the answer is six
verbatim spans. Thinking cannot improve copying, so turning it off costs nothing this product
claims. On a task that needed inference the trade would be the other way round, and the setting
would be a way to spend less, not to be right.

**What does not change.** The model still never emits a figure. The schema still has no numeric
field. The guard still runs on whatever comes back, and every span is still re-verified as a literal
substring of the user's own text.

**Verified, 2026-11-10, with nothing set.** `npm run check-model` against the model whose real
reading took 123.6 s, with `AI_REASONING_EFFORT` absent from the environment entirely:

```
model:    nvidia/nemotron-3.5-lightning:free
thinking: none (the default)
answered in 1597 ms with 1 span(s)
```

1.6 s where the same code path took over two minutes. `AI_REASONING_EFFORT=very-high` fails before
any request is sent, naming the accepted values; `AI_REASONING_EFFORT=default` restores the field-
free request for a stricter provider.
