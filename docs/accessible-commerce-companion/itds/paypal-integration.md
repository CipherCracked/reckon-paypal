# Accessible Commerce Companion — ITDs

| ITD 1 — *"Use Orders API v2 for one-time commitments and Subscriptions with Billing Plans for recurring ones, created server-side."* |  |
| :---- | :---- |
| **THE PROBLEM** | The product promises that the figures it shows are the terms actually agreed to. That holds only if the figures come from the payment system rather than the page being explained. Different commitment shapes are different objects in PayPal, and using one model for both loses the record the shopper needs to judge. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Orders API v2 for one-time commitments; Subscriptions and Billing Plans for recurring ones; both created server-side.**<br>2. Orders API only, with recurring payments modelled as repeated orders.<br>3. Subscriptions API as the only surface.<br>4. A hosted checkout outside our control. |
| **REASONING** | Each commitment shape should map to its native object. A subscription modelled as an order loses the renewal record and the plan terms — precisely the figures the shopper cannot derive. Using subscriptions for everything forces a one-time purchase into a false recurring product. Building either client-side puts the numbers where they can be altered. Server-side creation keeps the amount and its breakdown authoritative, which is what lets the companion attribute every figure to PayPal. |
| **TRADEOFFS** | Two integration paths instead of one, and a subscription flow requires product and plan setup before the first test. The financed path is not covered by either API in a way confirmed here. |
| **NOTES** | Whether PayPal exposes an instalment/Pay Later path usable in a sandbox developer account is unverified. If it does not, the third commitment shape is described in the interface but not integrated, and the demo says so. Recurring remains a purchase shape, not the payment primitive. **Update 2026-11-06 (sandbox):** an order cannot be captured until the payer authorises it — capture returns `ORDER_NOT_APPROVED` otherwise. Both shapes therefore hand the shopper to PayPal's own approval page: subscriptions via the subscription's `approve` link, orders via the order's `approve` link (surfaced by our route, with `return_url`/`cancel_url` built server-side from our own origin). On return, the consent screen captures the approved order. Still no PayPal JS SDK in the page. **Update 2026-11-10:** the financed path is integrated, as a billing plan — ITD 2 below. The sentence above ("described in the interface but not integrated") no longer holds. |

| ITD 2 — *"Use a PayPal billing plan with twelve cycles and a `setup_fee` to make a financed purchase a schedule of charges rather than one order."* |  |
| :---- | :---- |
| **THE PROBLEM** | The mattress screen promises twelve payments of $105.00 and shows $1,320.00 across the term. The order path sent one `CAPTURE` order for today's instalment, so PayPal collected payment one and nothing scheduled payments two to twelve. A figure the shopper is asked to judge is then backed by nothing: "across the term" is arithmetic on the page, not an agreement anywhere. This is the second half of the question opened in `todo.md` §6 — the first half being whether the $60.00 origination fee sits inside the twelve instalments or beside them, which is answered here because PayPal has to be told which one it is. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **A Billing Plan with one `REGULAR` cycle of twelve monthly charges at the instalment amount, and the origination fee as the plan's `setup_fee`.**<br>2. Keep the order path and label the financed screen as a reading demonstration rather than a payment one.<br>3. Schedule the instalments ourselves, creating future-dated orders or invoices.<br>4. Charge the whole term today and drop the instalment figure.<br>5. Use a PayPal Pay Later / instalment product meant for financing. |
| **REASONING** | A plan is the only PayPal object in which a schedule of charges exists as an agreement. Its `billing_cycles[].total_cycles` makes the term end at twelve, and `pricing_scheme.fixed_price` is one instalment, so what PayPal will collect is what the screen shows — the figure stops being a claim about the future and becomes a description of something PayPal holds. Option 3 moves the schedule into our code, which is the storage ITD 6 removed: a schedule we keep is a schedule we can lose, and PayPal would have no record of the payments we made up. Option 4 breaks the product's whole premise about a financed commitment. Option 5 is the right shape but unverified in a sandbox developer account, and the rule for this project is to ship what has been run, not what might work.<br>The fee lands where PayPal actually takes it. `payment_preferences.setup_fee` is collected once at activation, in addition to the first cycle — which is the seller's "plus", and settles §6 in the direction PayPal will charge: 12 × $105.00 + $60.00 = $1,320.00, fee once, not inside the instalments. Because it is taken on day one, "Charged today" has to include it ($165.00); the itemisation gained a "Fee taken once" row so the parts still add up to the figure they sit under. |
| **TRADEOFFS** | A financed purchase is a subscription at PayPal, so its plan terms read back as the `recurring` shape. The catalogue and the plan-side reader must therefore agree that the opening fee lives in `setup_fee` and is charged once — a disagreement would show one screen sharing the fee per period and another showing it once. Plans are immutable, so the fee and the cycle count are encoded in the plan's name; changing either creates a new plan, and a repeat run resolving by name finds only the plan that matches the terms currently published. Cancelling an instalment plan from the receipt is not offered: what ending the agreement mid-term costs the payer is stated nowhere, and the screen does not invent it. |
| **NOTES** | Verified live in the sandbox on 2026-11-10. `POST /api/paypal/subscriptions` for `mattress-financed` created plan `P-3E837483AP118242UNLZRRNQ`, named *"Commitment demo plan P-DEMO-MATTRESS-FINANCED 12x +60.00"*, with one `REGULAR` cycle, `interval_unit` `MONTH`, `total_cycles` 12, `fixed_price` `105.0`, `setup_fee` `60.0`. The coffee plan was re-read unchanged (12 × `12.0`, no fee). Full activation — the point where PayPal takes the $165.00 — still needs a sandbox buyer to approve, which is the open blocker in `todo.md` §7a. |
