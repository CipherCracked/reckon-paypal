# Accessible Commerce Companion — ITDs

| ITD 1 — *"Use Orders API v2 for one-time commitments and Subscriptions with Billing Plans for recurring ones, created server-side."* |  |
| :---- | :---- |
| **THE PROBLEM** | The product promises that the figures it shows are the terms actually agreed to. That holds only if the figures come from the payment system rather than the page being explained. Different commitment shapes are different objects in PayPal, and using one model for both loses the record the shopper needs to judge. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Orders API v2 for one-time commitments; Subscriptions and Billing Plans for recurring ones; both created server-side.**<br>2. Orders API only, with recurring payments modelled as repeated orders.<br>3. Subscriptions API as the only surface.<br>4. A hosted checkout outside our control. |
| **REASONING** | Each commitment shape should map to its native object. A subscription modelled as an order loses the renewal record and the plan terms — precisely the figures the shopper cannot derive. Using subscriptions for everything forces a one-time purchase into a false recurring product. Building either client-side puts the numbers where they can be altered. Server-side creation keeps the amount and its breakdown authoritative, which is what lets the companion attribute every figure to PayPal. |
| **TRADEOFFS** | Two integration paths instead of one, and a subscription flow requires product and plan setup before the first test. The financed path is not covered by either API in a way confirmed here. |
| **NOTES** | Whether PayPal exposes an instalment/Pay Later path usable in a sandbox developer account is unverified. If it does not, the third commitment shape is described in the interface but not integrated, and the demo says so. Recurring remains a purchase shape, not the payment primitive. **Update 2026-11-06 (sandbox):** an order cannot be captured until the payer authorises it — capture returns `ORDER_NOT_APPROVED` otherwise. Both shapes therefore hand the shopper to PayPal's own approval page: subscriptions via the subscription's `approve` link, orders via the order's `approve` link (surfaced by our route, with `return_url`/`cancel_url` built server-side from our own origin). On return, the consent screen captures the approved order. Still no PayPal JS SDK in the page. |
