# ITD 20 — Reading the Examples Ahead of Time

**Status:** Adopted (2026-11-10) — **built (2026-11-10)**
**Date:** 2026-11-10
**Answers:** Problem tree Q3 of `../intro.md` — *how does a one-click reading stay honest and fast on a ~47-second model*.
**Serves:** IPD 22, which cannot promise a reading in about a second unless the reading already happened.

| *"Read the example documents once at server start, cache the verified result by their text, and serve it."* |  |
| :---- | :---- |
| **THE PROBLEM** | `POST /api/read` calls the model on every request (`app/api/read/route.ts:49`), and one reading has been measured at roughly 47 seconds on the current endpoint, with the client allowing retries on top. The route is the product's only demonstration of AI doing work a script could not, and it is therefore the one screen that cannot afford to be slow. A visitor who has to wait most of a minute to see the product work will not wait. The cache that already exists for exit terms (`lib/commitment/published-exit.ts`) proves the pattern: module state does not survive Next's separate compilation graphs, so the cache lives on `globalThis`, and start-up reads fill it before a reader arrives. Nothing equivalent exists for documents. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **A `globalThis`-backed cache of verified readings keyed by the normalised document text, filled at server start for the example texts, with a time limit and in-flight de-duplication.**<br>2. Ship a static fixture per example in the repository and serve that response directly.<br>3. Cache in the browser after the first reading of each example.<br>4. Keep reading live and show a progress state for the wait. |
| **REASONING** | Option 2 is the one to reject on principle rather than on effort: a fixture is an answer recorded once and served as if it had been computed now, and it cannot tell the difference between the model as it behaved when the fixture was made and as it behaves today. It also cannot answer a visitor's own text, so the product would have two kinds of answer — one canned, one real — with no visible line between them. Option 1 stores what the server actually computed from that exact text, so the cached answer is a real reading of that document; it simply happened earlier. That distinction is the same one the exit cache already relies on, and it is honest as long as the screen does not imply the model ran in the last second. Option 3 helps only the second visitor of a browser, and the judge is the first. Option 4 accepts the wait that stops the demonstration from starting. The cache key must be the normalised text, not the raw paste: `normaliseText` already collapses whitespace and unifies quotes and dashes, so a sample re-typed with different spacing still hits. It does **not** fold case, and the key must not either — a cached response carries spans in the casing of the text it was read from, and lowercasing the key would serve those spans for a differently-cased document. In-flight de-duplication matters more here than for exit terms, because a warm-up and a first click can overlap. |
| **TRADEOFFS** | The cache holds whole readings, up to the route's 20,000-character limit per entry. **Two lifetimes, not one.** The example texts are static content: their readings are computed once and never expire, or the warm-up only helps the first ten minutes of a process's life, which is precisely the wrong window for a judge who arrives later. Visitor documents expire — a short life, matching the exit cache — and the store is bounded by **count** with the oldest entries dropped, because a time limit bounds age and not growth. A cold deploy has no cache until `register()` has run and the model has answered, so the first click after a restart is still slow and must say so. Failures are not cached: a transient network error should be retried on the next click, not remembered for the life of the process. |
| **NOTES (lifecycle)** | The refusal example is warmable too: it produces a complete candidate-mode response, and that response is what is cached — the cache stores completed answers, not only answers that produced figures. |
| **NOTES** | `instrumentation.ts` already calls `warmPublishedExits()`; the example warm-up belongs beside it, guarded by the same `isModelConfigured()` check — with no model, every example would read "could not be interpreted", and caching that would turn the demonstration into its opposite. The response must say what the visitor is looking at: a reading of *that text*, computed once, not a claim about the last second. The cache is not per-person and stores no person's document beyond the text they submitted; a document the route refuses (too short, too long, unparseable) is not cached. |
| **NOTES (built, 2026-11-10)** | Built as decided, in three files rather than one. `lib/document/answer.ts` builds the answer for one text and reports an `Attempt` — the answer plus whether it is a fact about the *document* (`keep: true`) or about this *attempt* (`keep: false`). `lib/document/reading-cache.ts` holds the `globalThis` maps and is the only thing that decides what may be remembered; the route now validates, asks the cache and sends the JSON, and reads nothing itself. `lib/document/warm.ts` walks the example texts in order at start-up. |
| **NOTES (what "a failure" turned out to mean)** | The route could not tell two failures apart: `readDocumentWithModel` throws both when the model never answered and when it answered with no usable span. They are not the same fact — the first is one bad minute, the second is a reading of that text — so the attempt is marked unkeepable only when the error is *not* `UnreadableDocumentError`. Without that distinction the refusal example, whose correct answer is often "no usable span", would have been re-read on every click for the life of the process. |
| **NOTES (no ceiling needed)** | `published-exit.ts` carries a three-minute ceiling because a promise that never settles would hold its slot forever. Nothing equivalent is here: the model client owns the timeout (45 s) and the retries (2), so every attempt settles, and a second defence would be a second thing to get wrong. The identity check on release is still there — the slot is only cleared by the attempt that holds it. |
| **NOTES (one pass, not a burst)** | Measured live on 2026-11-10 against the configured free endpoint: four exit readings fired at once gave **one answer in 37 s and three still waiting a minute later**; the same calls in sequence gave 21 s, 58 s and success for each. `warmPublishedExits` now awaits each text in turn rather than firing the set, and the same rule must govern the example warm-up this decision adds: warm sequentially, or the warm-up starves itself and every screen shows "could not be read" while it does. A page render never adds a request of its own when a reading is already in flight — it joins it (`published-exit.ts`'s `inFlight`). |

## Wiring

- New module beside `warm.ts`: keyed on `normaliseText(text)`, storing `{ response, at }`, with `inFlight` de-duplication and a TTL, on `globalThis` for the same reason the exit cache is.
- `app/api/read/route.ts` — check the cache before calling `readDocumentWithModel`, and store every **completed** response (a reading or a candidate-mode answer); never store a thrown failure.
- **Deploy target.** No route declares `maxDuration` and there is no `vercel.json`. A 47-second model call will exceed the default function limit on most serverless hosts, so whichever host is chosen must either allow it or the warm-up is the only path that works. The target must be named before this is built; a host with a short default silently turns the reader into a fallback.
- `instrumentation.ts` — warm the example texts; no-op without a model.
- A test that a warmed example answers without calling the model, and that an unconfigured server skips the warm-up entirely.
