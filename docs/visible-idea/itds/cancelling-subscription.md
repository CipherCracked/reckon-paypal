# ITD 21 — Cancelling a Subscription at PayPal

**Status:** Adopted and built (2026-11-10)
**Date:** 2026-11-10
**Answers:** Problem tree Q4 of `../intro.md` — *what PayPal makes possible at the moment of leaving, and what the product may claim afterwards*.
**Serves:** IPD 23, whose action has to be a platform operation, not a message.

| *"Call PayPal's cancel on the subscription id, and report PayPal's answer rather than our own."* |  |
| :---- | :---- |
| **THE PROBLEM** | The product creates subscriptions (`lib/paypal/subscriptions.ts:115`) and never touches their lifecycle. The receipt's only help is a link to PayPal's autopay page (`app/receipt/[orderId]/page.tsx:19`). PayPal models cancellation explicitly — `POST /v1/billing/subscriptions/{id}/cancel` — and the product already holds the id in the receipt route. Nothing technical prevents the action; it was a product decision not to offer it. The technical questions are what the call returns, what it means when it refuses, and how the screen reports an operation whose result it cannot observe again later, given that the product keeps no state (ITD 6). |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **A server route per subscription id that posts the cancel, maps PayPal's reply to one of three outcomes, and returns it; the receipt reports that outcome and offers nothing further.**<br>2. Keep the link to PayPal's autopay page and add instructions.<br>3. Record the cancellation in our own store so the receipt can show its own history.<br>4. Subscribe to PayPal webhooks and reflect the lifecycle asynchronously. |
| **REASONING** | Option 1 mirrors the shape that already works: a thin route over one PayPal operation, with the result passed through rather than interpreted (`app/api/paypal/orders/[id]/capture/route.ts`). The id is already in the URL; no state is needed to perform the act, and none is created by it. Option 3 contradicts the decision that the product keeps nothing about a person, and would create a record that can disagree with PayPal — the one source the receipt trusts. Option 4 is the production-grade answer and the wrong change for two days: it answers a question the product does not ask (what happened later), and its absence is not a defect of the cancel action, which returns its own result synchronously. Option 2 is the state being corrected. The reply must be read carefully. PayPal answers a successful cancel with no body; a subscription that is not in a cancellable state answers an unprocessable-entity error carrying an issue code. Those are two different facts — *we ended it* and *it was not running* — and both are true outcomes to show. A third state exists and is the one easiest to get wrong: a call that neither succeeded nor was told no — a timeout, a reset, a 5xx — tells us nothing about whether PayPal committed, and it must be reported as unknown rather than folded into either of the other two. Treating either error as success would be the same failure the capture route refuses when it declines to call `PENDING` complete. Nothing may be claimed beyond what the reply said: no "no further charges will be taken" unless PayPal said the subscription is cancelled. |
| **TRADEOFFS** | Cancellation is irreversible at PayPal; there is no restore, so a mistaken cancel can only be undone by subscribing again — the confirmation step in IPD 23 is the only guard. The route takes the subscription id from the URL and the product has no session, so possession of the id is the only authorisation; acceptable for sandbox payments, not for a live deployment, and it should be stated rather than discovered. Because nothing is stored, the screen cannot show a history of the action, only its immediate result; a reload afterwards will read the subscription's new state from PayPal, which is the truthful account and may say less than the moment did. |
| **NOTES** | Mapped outcomes, three not two: **cancelled** — PayPal returned 2xx (no body); **not running** — an error whose issue says the subscription was already cancelled or is not active, reported in PayPal's words; **not confirmed** — any other failure, a timeout, or a dropped connection, reported as *"we cannot tell whether that went through — check PayPal"*. The third state is the corrected one: a request that failed after PayPal had already committed is not evidence that nothing happened, and reporting it as "nothing has changed" would be a claim the product did not observe. The reason field is optional at PayPal and should carry a fixed, honest sentence ("Cancelled from the receipt for this subscription") rather than anything derived from a person. The subscription must be re-read before offering the action, so a commitment PayPal already ended does not present a live button. Unverified against the live sandbox until the buyer-approval check in `todo.md` is done; the mapping is written from PayPal's documented responses and should be tested against a real reply before the demo. |
| **NOTES (receipt state)** | The action cannot be shipped against the receipt as it stands. `isSettled` accepts only `COMPLETED` and `ACTIVE` (`lib/paypal/retrieve.ts:111-113`), and every other state is answered early with *"PayPal has not confirmed this payment, so there is nothing to record yet. Nothing has been taken."* (`app/receipt/[orderId]/page.tsx:79-89`). A subscription this action has just cancelled would therefore produce a record that says nothing was ever taken — after the shopper paid, possibly for months — and the "already cancelled" outcome would be unreachable. **`CANCELLED` must be settled on its own terms**: the record renders, shows what was paid as PayPal states it, and says separately that PayPal reports the subscription cancelled. Building the cancel route without this makes the product lie about money, so the two land together. |
| **NOTES (deploy)** | No route in the project declares `maxDuration` and there is no host config, so the default function limit applies. The receipt itself already awaits `resolveExitTerm` with a budget, and this route adds a second PayPal call on top of a page that reads; on a host with a short default the cancel can be killed mid-request — which is exactly the case the **not confirmed** outcome exists for, but only if the route is allowed to answer at all. The host and its limit must be named before the demo rather than discovered during it. |

## Wiring

- `lib/paypal/subscriptions.ts` — `cancelSubscription(id)`, using the existing `paypalRequest` and `withinDeadline`.
- `app/api/paypal/subscriptions/[id]/cancel/route.ts` — POST, maps the reply to the three outcomes, never throws for a non-2xx PayPal answer.
- `components/CommitmentRecord.tsx` — the confirmation, the call, and the outcome beside the cost-to-leave figure.
- `lib/paypal/retrieve.ts` — `CANCELLED` becomes a settled state, so the receipt renders the record instead of the "nothing has been taken" early return.
- Tests: success, already-cancelled, timeout or network failure, that a failure is rendered only as **not confirmed** and never as a cancellation, and that a cancelled subscription still produces a receipt showing what was paid.

| **NOTES (live check, 2026-11-10)** | `POST /api/paypal/subscriptions/I-ZZZZZZZZZZZZ/cancel` → `{"outcome":"not-running","issue":"INVALID_RESOURCE_ID"}` in 0.65 s. The credentials, the path, the POST and the error mapping are verified against PayPal for real. A malformed id (`I-FAKE0000000`) answers `400 INVALID_PARAMETER_SYNTAX`, which this route deliberately reports as **not confirmed** — see the next row. The 2xx success path is **not** live-verified: ending a running subscription needs an `ACTIVE` one, and the only subscription on this sandbox is `APPROVAL_PENDING` (buyer login is the user's, `todo.md` §1). |
| **NOTES (malformed id)** | PayPal validates the *shape* of the id before it looks one up: `I-` + 12 alphanumerics. Anything else answers `400 INVALID_PARAMETER_SYNTAX`, which is not a statement about a subscription and so is not mapped to `not-running`. It falls through to **not confirmed**, whose sentence ("we cannot tell whether that went through") is wrong for it — nothing went through. Left as it is, deliberately: the id on the page always came from PayPal's own redirect, so the branch is unreachable from the product, and widening `NOT_RUNNING` to cover a bad request would make a real malformed request look like a subscription that had ended. A future deployment that takes ids from anywhere else must separate the two. |
