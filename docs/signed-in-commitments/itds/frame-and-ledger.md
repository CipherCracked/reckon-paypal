# ITD 24 — The Frame Reads the Session, and the Ledger Look

| ITD 24 — *"Use a session-reading root layout and a token-level ledger visual system to put the way in where people look and make the figures the loudest thing on the page."* |  |
| :---- | :---- |
| **THE PROBLEM** | IPD 27 puts the account control in the frame, on every screen. That raises a mechanism question the frame has never had to answer: it must know whether someone is signed in, and whether signing in can work at all on this deployment, before it renders a word. The frame is a server component shared by eight routes, none of which passes it state today, and the honest answer must not flash the wrong one — a *Sign in* link that becomes *Your commitments* after hydration is a worse lie than either label. <br><br> The same change exposed a second problem. The visual language is the browser's: a system font stack, cream paper, `12px` corners, pill buttons, and the same weight for the seller's paragraph as for the money. Nothing on the page says which numbers matter, on a product whose entire claim is that three figures are readable and sourced. For an audience of adults with dyscalculia, dyslexia and ADHD, that is not a style preference; the figures are the content. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Read and verify the session cookie in the root layout, pass `signedIn` and `canSignIn` into `Shell`, and render one account control beside the text-size control. Restyle at the token layer: a legibility typeface for text, a monospaced face with tabular figures for every amount, near-black ink on paper with one deep-green accent, `2px` edges and hairline rules.** <br> 2. A client component that fetches the session from an API route after mount and renders the control then. <br> 3. Leave the frame static and keep every account control on the account page. <br> 4. Restyle screen by screen, leaving the tokens alone. |
| **REASONING** | The cookie is a signed string, so verifying it is arithmetic on the request, not a query: a layout that parses it costs one HMAC per render and knows the truth at the first paint. Option 2 costs a request, a loading state, and a visible flip from *Sign in* to *Your commitments* on every navigation — for a person who has just told a site their money is hard to read, a header that changes under them is the opposite of the reassurance the frame exists to give. Option 3 is IPD 27's rejected placement. <br><br> The frame must also stay silent where it would be false. `canSignIn` is the conjunction ITD 22 already requires — a client id, a secret, `SESSION_SECRET` — so a deployment without them renders no account control at all rather than a link to a page that says signing in is switched off. The header is a claim, and it is held to the same rule as every figure. <br><br> The restyle is a token edit because ITD 15 already made every colour, size, radius and space a custom property and every rule consume it. Option 4 would have meant editing eight routes' worth of rules by hand, and the pages would drift apart within a week — exactly what ITD 15 was written to prevent. <br><br> Two choices inside the restyle carry the argument. **Atkinson Hyperlegible** is a typeface drawn by the Braille Institute for low vision: using it here is the product's thesis made visible rather than described, and its slightly wider forms survive the large text size the frame offers. **Mono for money** is the ledger convention: monetary figures in a fixed-width face with `tabular-nums` line up across rows, so *across the term* and *charged today* can be compared by eye rather than by reading two labels. The accent is a deep green used only for actions and the signed-in state, so colour never carries a figure's meaning. |
| **TRADEOFFS** | Reading cookies in the root layout makes every route render per request. None of the payment screens was static, so the visible cost is limited to the two screens that were not already dynamic, and the cookie is a fixed-size string that never grows. <br><br> The typefaces are fetched and self-hosted at build by `next/font`, so a build with no network fails here — the risk of a font CDN at runtime is traded for a build-time dependency. Both faces carry a full fallback stack for the case where the files are missing. <br><br> A sharper palette with `2px` edges reads as a ledger rather than a consumer app, which is the point, and it also lowers the surface's visual warmth; contrast rises where warmth falls, and every pair in the file is still checked against WCAG 2.2 AA in both themes. <br><br> Mono is wider than proportional type: a long amount at the largest text size is the case most likely to overflow a phone card, so figure rows wrap to one column before the amount can push the card. |
| **NOTES** | The text-size control still multiplies the root `font-size`, and every size in the file is in `rem`, so the new scale inherits it without a second mechanism. The account control is text, not a hop to PayPal: *Sign in* opens the account page, which says what signing in reads and keeps before offering the button (IPD 27). |
