# ITD 22 — Identity and What Is Kept

| ITD 22 — *"Use Log in with PayPal and a signed cookie to know who is asking."* |  |
| :---- | :---- |
| **THE PROBLEM** | The signed-in page (IPD 25) needs to know whose subscriptions to look for. The product has never had an identity: every route is anonymous, the receipt is keyed by PayPal's own id, and the only thing on the person's machine is a text-size preference in `localStorage` (`lib/preferences.ts`). Whatever mechanism is chosen also decides whether the claim *"nothing is stored"* — printed on the receipt, in the README and in the judge brief — survives. A session that lives on our server would make that claim false; identity that lives only in the browser keeps it true in the sense people mean it. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Log in with PayPal (Identity API, authorization-code flow, `openid profile email`), then a signed `httpOnly` cookie carrying the payer id, the verified email and an expiry. No server-side session, no database, no user record.** <br> 2. An email-and-password account of our own: registration, hashing, reset flow, a users table. <br> 3. No session at all — the person proves who they are on every visit and the page holds the payer id in memory. <br> 4. PayPal identity plus a server-side session store (Redis or a table) keyed by a session id. |
| **REASONING** | The identity should come from the party that holds the money, because it is the only party that can verify it. Option 2 makes us a custodian of credentials for a demo that processes no credentials at all, and it stores exactly the record the product says it does not keep; it is also the option most likely to be breached, since a solo hackathon build is not where password handling should be invented. Option 1 delegates verification to PayPal and stores *nothing a person would mind losing* — a payer id and an email that PayPal already holds and already shares with every merchant they pay. <br><br> The cookie is state, and the honest description of it matters more than its size. It lives on the person's own machine, it is `httpOnly` and `Secure` in production, it expires, it authorises reads only, and deleting it signs them out. Option 4 would move that state onto our disk, at which point *"nothing is stored"* becomes *"nothing is stored except who you are and when you were here"*, and the receipt screen — the one a judge inspects — would be lying in small print. Option 3 has no storage at all and pays for it with a round trip through PayPal on every navigation, which is the friction that made the receipt link necessary in the first place. <br><br> Signing with an HMAC rather than trusting the payload is not optional: an unsigned `payer_id` cookie would let anyone read anyone's record, which for this product is the whole of the harm. `SESSION_SECRET` joins `env.example`; a missing secret must fail closed (sign-in unavailable, stated) rather than degrade to unsigned. |
| **TRADEOFFS** | A stolen cookie is a read-only impersonation for its lifetime, so the lifetime is short (two hours) and the cookie carries no capability beyond *"show me this payer's records"*. There is no server-side revocation: signing out deletes a cookie the person holds, and a copy taken before that stays valid until it expires. <br><br> The flow depends on a **dashboard step that code cannot perform** — *Log in with PayPal* must be enabled on the sandbox app with a registered return URL (probed 2026-11-11: the connect endpoint answers *"invalid client_id or redirect_uri"* today). Until that is done the entry point must render the "could not check" state of IPD 26, not a broken button. <br><br> PayPal's userinfo returns `user_id`, documented as the payer id. It is matched against `subscriber.payer_id` only after one live check against a known record (`D5CKAUQ8V7ADL`); if they disagree, matching falls back to the verified email and the page says which key it matched on. |
| **NOTES** | The claim on the receipt changes from *"Nothing is stored"* to a sentence that is true with a session: we keep no record of the purchase — PayPal holds it, the person holds the link, and the browser holds a sign-in that expires. That edit belongs with this decision, not after it. Scopes requested: `openid profile email` only. No `address`, no `paypalattributes`. |
