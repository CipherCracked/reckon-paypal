# ITD 38 — The Agreement's Own Transactions, Within a Budget

| ITD 38 — *"Read the agreement's own transactions within a page's budget, sum them in minor units, and let the model write only numerals the server handed it."* |  |
| :---- | :---- |
| **THE PROBLEM** | The receipt is to state what PayPal's record says it has taken (IPD 45), and to show a plain-language sentence over those facts written by the model (IPD 46). Four measurements constrain how. Transaction Search (`GET /v1/reporting/transactions`), the one call that would answer for every payment at once, answers **403 NOT_AUTHORIZED** with this app's credentials. The per-agreement endpoint, `GET /v1/billing/subscriptions/{id}/transactions?start_time&end_time`, answers — one `COMPLETED` $24.99 record per cancelled subscription — but it requires a window, and every record in it carries `payer_name` and `payer_email` beside the amount. The plan behind each agreement states six monthly cycles at $24.99, so the fact the screen needs is *1 of 6 · $24.99* against *$149.94*. The model answers in 3–6 seconds warm and 15.7 cold, which is longer than a receipt may hold a render for a sentence it does not need. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Read `/v1/billing/subscriptions/{id}/transactions` inside a detail-read budget, windowed from the subscription's `start_time`, counting only `COMPLETED` and summing `gross_amount` in minor units; keep the payer fields out of the parsed type entirely. Build the line on the server from that plus the plan's cycle count. Write the sentence on a route after the page renders, from facts the route re-reads from PayPal, gated by a numeral allow-list and cached by the facts.** <br> 2. Use Transaction Search for a merchant-wide view, and filter to the agreement. <br> 3. Derive *1 of 6* from the plan's cadence, the start time and today's date, and read no transactions. <br> 4. Keep a local record of what was taken — written at capture, or from webhooks — and read that. <br> 5. Generate the sentence during the render, under `withBudget(..., MODEL_READ_DEADLINE_MS, null)`. <br> 6. Have the browser send the figures it rendered, and let the route write a sentence over them. |
| **REASONING** | The deciding factor is **which source can answer for this agreement, honestly and within the credentials the product has**. Option 2 is closed by measurement, and it is also the wrong question: a merchant-wide search returns every payer's payments, which this product has no business holding in memory, let alone naming on a screen. Option 3 is the arithmetic-as-record mistake IPD 45 rejects. Option 4 contradicts ITD 6 — this app stores nothing about a person's payments, so that a copy can never go stale against PayPal's — and would need a migration, a webhook endpoint and a retention story for one line. The per-agreement endpoint is the only source that is both readable and about the right thing. <br><br> The window comes from PayPal, not from us. The endpoint refuses a request without `start_time` and `end_time`, and the subscription's own `start_time` is the only honest lower bound: a payment for this agreement cannot precede it. `end_time` is now plus a day, because PayPal compares in the merchant's calendar and a boundary at the current instant can clip a payment made in the same second. When PayPal omits `start_time`, the reader falls back to three years back rather than to the process start or to yesterday; three years is PayPal's own retention horizon and the widest window the endpoint is documented to answer. <br><br> `COMPLETED` alone is counted, because the word *taken* means money that has moved and stayed. `APPROVED` is an authorisation with no capture, `PENDING` is not yet a payment, and `REFUNDED` and `PARTIALLY_REFUNDED` are money that came back — a line that counted them as taken would state a charge PayPal's own record says was reversed. Every other status is dropped from the count, and the reader never sees it, because the product has no honest sentence about a payment it did not read. <br><br> The sum is integer minor units, like every figure in this codebase (ITD 2): `parsePayPalAmount` and `fromDecimalString` split the wire string rather than multiplying by a hundred, and `addMoney` adds integers. Floating point would eventually print $74.969999 for three payments, on the one screen that is printed and kept. <br><br> The payer fields are excluded by the parsed type, not filtered afterwards. `PaymentRecord` names three fields — `time`, `status`, `amount` — and the reader never writes the response body to a variable, a log or a cache key. A test feeds a transaction carrying a name and an email and asserts the resulting record's JSON contains neither, so the exclusion is pinned at the boundary rather than trusted to review. <br><br> The sentence does not run during the render. Option 5 looks natural and is the wrong budget: three seconds against a measured 3–6 warm means the sentence is usually abandoned, and the receipt — the page a shopper keeps — would wait for a decoration. Option 6 is rejected because of what the guard is for: the claim is that every numeral in the model's sentence is one PayPal supplied, and a numeral the browser supplies is not. The route takes a subscription id, re-reads the agreement and its payments from PayPal, derives the facts itself, and asks the model; the id is validated by shape before any request is made. That doubles the PayPal reads for a view — the page reads the agreement for its figures, the route reads it again for the sentence — which is the price of the server never trusting a number it did not read. <br><br> The guard is an allow-list, not a ban. `assertNoMoney` refuses any figure in output where the model was given none; here the model is given figures, so the rule inverts: `findUnknownNumeral` collects every digit run and every spelled number in the sentence, normalises `$`, commas and spaces away, and refuses the whole sentence if one is not in the set the server built from the facts. Hyphenated number words are summed so *twenty-four* is compared as 24 rather than as 20 and 4. It is deliberately conservative: *"one of them"* in a state where 1 is not an approved figure refuses a truthful sentence. The fallback is the exact line from IPD 45, which is always right, so the cost of a false refusal is an explanation the reader did not get — not a fact they were denied. <br><br> The sentence is cached against its facts — subscription id, completed count, taken amount, term count, term total — so a second view of the same state costs nothing, and a new payment changes the key and earns a fresh sentence. In-flight duplicates are shared, because a client component's effect runs twice in development and neither run should pay for a model call. |
| **TRADEOFFS** | The receipt now makes two more PayPal reads per view, and the sentence route repeats them; measured sandbox latency is a few hundred milliseconds each, sequential, against a page that already reads the agreement and its plan. <br><br> Nothing before `start_time` is read, and no payment can exist there for this agreement — but if PayPal omits `start_time`, the three-year fallback is a guess, and the screen does not say so. The line would still be built from real transactions; only the window's completeness is assumed. <br><br> A refunded payment disappears from the count, so *taken* means *still taken*. The screen cannot say money came back, and a shopper who was refunded and charged again sees one completed payment where PayPal's ledger holds three events. The non-goal in the decomposition is explicit about this. <br><br> The guard is blind to meaning. *"Almost all of it"* and *"only $24.99"* contain no numeral the allow-list can catch; the prompt forbids comparison, evaluation and prediction, and the exact line sits above the sentence so the reader has the figures one line away. A test can pin the sentence's numerals; nothing can prove its fairness. <br><br> The sentence is generated by a route that costs a model call and PayPal reads on every uncached view. That is one endpoint a visitor can cause work through without signing in, bounded by the fact-keyed cache and the route's budget — the same exposure `/api/read` already has, and smaller, because the inputs are a subscription id rather than arbitrary text. |
| **NOTES** | `lib/paypal/transactions.ts` — `retrievePaymentsTaken(id, startedAt)`, `PaymentRecord`, and a `TakenRecord` of `{ kind: "read"; count; amount; }` or `{ kind: "unavailable" }`; never throws. `SubscriptionRecord` gains `startedAt`, read from `start_time`. <br><br> `lib/commitment/taken.ts` — the facts and the seven sentences of IPD 45, pure and tested one state per test. `lib/ai/record-words.ts` — the tool, the prompt, the facts-to-allowed-numerals conversion. `lib/ai/guard.ts` — `findUnknownNumeral` and `OnlyKnownNumeralsError`. `app/api/record/words/route.ts` — POST, id validated by shape, `withBudget(..., 20_000, null)`, successes cached, failures answered `{ sentence: null }` with 200. `components/RecordWords.tsx` — client, fetches after mount, renders nothing until a sentence exists. <br><br> The route answers 200 with `{ sentence: null }` for every failure it can name — wrong id, PayPal unreachable, model refused — because the sentence is decoration and the page must not show an error for it. A malformed id is the one 400. <br><br> Nothing about a transaction is ever logged. The body is parsed into a record that cannot hold a payer; the reasons a read failed are PayPal's status code, carried in `PayPalError`, and never the body. |
