# ITD 32 — A Pasted Link Resolves First

| ITD 32 — *"Use the catalogue's URL lookup and a read-back before redirecting, so a pasted link opens a product this app can actually show."* |  |
| :---- | :---- |
| **THE PROBLEM** | IPD 36 puts a field under the shop's search for a product URL. The catalogue resolves any product page with `POST /v1/lookup`, but its answer is not the same guarantee as a browse result: a listing from a merchant outside the catalogue *resolves for display purposes* and is not promised to the endpoints that read a product by id. <br><br> The product page (`app/product/[slug]/page.tsx`) opens a listing with `readMarketProduct(slug)` → `GET /v1/products/{id}` and answers `notFound()` when the catalogue returns null. A redirect straight from a successful lookup to `/product/ch3-<id>` would therefore land some shoppers on a 404 — after the shop had told them the link resolved. <br><br> The failure vocabulary is also wider than anything the shop has today: lookup answers 404 for a listing it cannot find, 422 for a URL that is not a product page at all, and may simply not answer. Those are three different sentences (IPD 36), so the call has to report them apart. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **`/shop?link=<url>`: validate the address, look it up, read the product back by id, and redirect to `/product/ch3-<id>` only when the read-back succeeds. Otherwise render the shop with the matching sentence and the field still filled.** <br> 2. Redirect on the lookup alone and let the product page's own "could not be read" screen handle the rest. <br> 3. Store the looked-up product in a short server-side map keyed by a token and redirect to `/product/link/<token>`. <br> 4. Do the lookup in the browser from the shop and route with the client router. |
| **REASONING** | The deciding factor is **the promise the redirect makes**. Sending someone to a product page is a claim that the page exists; a 404 on arrival contradicts what the shop just said, and the contradiction is visible to exactly the person this product is trying to reassure. The read-back costs one cached catalogue call — the same call the product page would make a moment later — and turns the claim into a fact. Option 2 is rejected because the product page's failure sentence (*This product could not be read*) is written for a link that was already in hand, not for a link the shop had just accepted. <br><br> The second factor is **what the URL has to carry**. The result is a product the product page can open by id, so the redirect target is the same `/product/ch3-<id>` a grid card produces. One product, one URL, no token: a link the shopper copies from the address bar is the same link anyone else can open later. Option 3 invents a second address for the same product and a server-side map with a lifetime the product has never needed. <br><br> Option 4 is rejected because the shop is a server component whose whole state is a URL (IPD 34): the lookup would need a client fetch, a loading state, and a second copy of the catalogue's key handling in the browser. |
| **TRADEOFFS** | A pasted link costs two catalogue calls before the redirect — the lookup and the read-back — and the first can take seconds when the catalogue has never met the retailer: up to twenty, the deadline it was given once the build measured the real thing (NOTES). The shop has to render that wait rather than a blank page, and the build found that it cannot — a route-level loading screen and a server redirect do not both happen (NOTES). <br><br> The read-back can fail for a product the lookup just returned (an outside-catalogue listing). The shop then says the link resolved but this app cannot open it — a fourth sentence, rarer than the other three but real. <br><br> The address is validated before it is sent: `https` only, a length cap, and a refusal for any host that belongs to this app. The fetch itself happens at the catalogue, so the guard is about not sending the shop's users into a redirect loop or a junk request, not about protecting a server we own. |
| **NOTES** | The lookup is cached like every other catalogue read, keyed by the URL, so a link opened twice costs one call. <br><br> The failure sentences are chosen by the outcome, not by the HTTP status: a 422 and a 404 read differently to a shopper even though both are "that link did not work", and a timeout is a third thing. <br><br> `redirect()` runs after the read-back, so an unreachable catalogue is a rendered sentence rather than Next's error page — the same rule the front door learned (`app/error.tsx`, 2026-11-12). <br><br> **As built, 2026-11-12. The wait is not rendered, and the redirect is why.** The obvious way to honour "render the wait" is a route-level `app/shop/loading.tsx`, and it was written: a line reading *Reading the catalogue…* while the lookup ran. It broke the feature it was decorating. With that file present, `GET /shop?link=<a product page>` answered `HTTP/1.1 200` with a body that stopped at the loading line; with it removed, the same request answered `307` and `location: /product/ch3-4iVGQw1`. A `loading.tsx` is a Suspense boundary, and a `redirect()` thrown inside a streamed boundary has already committed the 200 — Next cannot turn a response that has begun into a 307, so the shopper got a page saying the link was being read and then nothing. There is no arrangement of `loading.tsx` and `redirect()` that gives both, so the redirect keeps its promise and the wait is the browser's own: the shop's previous screen stays up until the server answers. The cost is a pause with no explanation, and it is paid only by someone who pasted an address, against a promise (the page exists) that a spinner cannot make. <br><br> **The deadline was measured, not guessed, and the first guess was wrong.** A lookup took the detail-read deadline of 8 s on the reasoning that it is another cost-of-showing-this-page read. Against the live catalogue it reported *The catalogue did not answer in time* for a page the catalogue was about to answer: a product page took 3.4 s, a collections page 7 s, a home page 13.5 s — the slow ones being the pages that turn out not to be product pages, because the catalogue has to fetch them to find out. A 15 s retry still timed out on a 17.5 s request. `LOOKUP_DEADLINE_MS` is 20 s (`lib/deadline.ts`), which covers the measured worst case with room; after the change the same request answered *That address is not a product page*, which is the sentence the shopper needed. |
