# ITD 30 — Reading the Catalogue for a Shelf

| ITD 30 — *"Use one module of browse, category and lookup calls, with paging, caching and named failures, to give the shop a catalogue behind it instead of a search box."* |  |
| :---- | :---- |
| **THE PROBLEM** | `lib/market/channel3.ts` knows two calls: `POST /v1/search` with a hardcoded limit of 12, and `GET /v1/products/{id}`. Everything the shop will become (IPD 33's shelf, IPD 34's categories, price narrowing and paging, IPD 36's pasted link) needs endpoints it has never called: `GET /v1/categories`, `POST /v1/browse` and `POST /v1/lookup`. <br><br> Each has a shape the screen has to respect. Browse **must** be scoped by a category, brand or website id, and refuses an unscoped call with a 422 — so a shop that wants a default view has to have chosen a category. Both browse and search return `next_page_token` and cap at 30 per page; browse caps at five pages and answers 422 for a token past the fifth. Lookup answers 404 for a listing it cannot find and 422 for a URL that is not a product page, and the shopper needs to be told which. <br><br> The module's existing cache is keyed by query text and assumes a single page, and its request helper turns every non-OK answer into one `MarketError`. Both assumptions stop being true the moment paging and lookup arrive. <br><br> Verified live on 2026-11-12: browse of `home-garden` returned 30 products and a token, and its products' categories were children of the requested root (`throw-pillows`, `mugs`, `portable-hot-tubs`) — so a root category does browse its whole subtree, which the shelf depends on. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Add the four calls to `channel3.ts` beside the two that exist, sharing one parser and one cache, with a page-aware result shape and a lookup outcome that distinguishes "not a product page" from "not found".** <br> 2. Build a second module for browsing so search is untouched. <br> 3. Use the catalogue's SDK (or its CLI) for the new calls. <br> 4. Do the filtering and paging on our side over a large search response. |
| **REASONING** | The deciding factor is **one parser, one set of rules**. A browse response is the same `SearchResponse` — products with offers, images and brands — so the code that already drops an offer without an exact price, refuses a non-https image and names an absent image is the code that must run for a shelf. A second module would either duplicate those rules or quietly skip them, and the shop would begin showing products the product page cannot price. Option 2 is rejected for that reason. <br><br> The second factor is **what the caller has to be able to say**. The shop's sentences (IPD 34, 35, 36) are different for an empty page, an unscoped catalogue, a dead link and an unreachable catalogue, so the module cannot collapse everything into one error. Search and browse return `{ products, nextToken }`; lookup returns a named outcome union — `found`, `not-a-product`, `not-found` — and throws only when the catalogue itself could not answer. `MarketError` keeps its status so a caller can still tell 422 from 500. <br><br> Option 3 is rejected because the product is judged on not hiding its mechanisms behind a vendor SDK, and because the SDK's types would put a vendor's names in our screens. Option 4 is rejected because the catalogue's own filters are the facts the shelf shows — filtering a page of twelve in memory would show a shopper an empty shelf that a real query fills. |
| **TRADEOFFS** | Four more endpoints means four more cache keys and four more ways for a page to be slow. The cache grows from two maps to four, keyed by the parameters the URL carries, so a page is as cacheable as its link. <br><br> The price bands cross a unit boundary: the catalogue takes dollars and cents as numbers, and the app keeps every amount in integer minor units. The conversion lives in one place, with its own test, because a band boundary off by one cent is invisible until a product priced at exactly $50.00 lands on the wrong page. <br><br> Lookup is the first call whose latency is the retailer's, not the catalogue's: an uncached URL can take seconds. It was to get the same deadline as a detail read; building it proved that wrong, and it has a longer one of its own (NOTES). |
| **NOTES** | Paging is passed through as an opaque token, never parsed — the catalogue's token format is not ours to understand. The URL carries it verbatim. <br><br> The module keeps dropping products with no in-stock USD offer (`buyable`). The shop's promise is that every price it shows is one someone can pay; the cost is that "no results" can mean "results we could not price", which the empty-state sentence must allow for. <br><br> Categories are cached for longer than products: a taxonomy does not change between two page loads the way a price does. <br><br> **As built, 2026-11-12.** Three things the catalogue settled that the decision had assumed. *A slug is an id.* `filters.category_ids` accepts a category slug even though the field is named for ids, and `category_slugs` is a 422 — so the shelf's links carry the slug the taxonomy returned and the module sends it unchanged, with no lookup table in between. *A lookup needs a longer deadline than a page read.* Eight seconds reported a slow lookup as no answer at all: measured twice each on 2026-11-12, a product page took 3.4 s and two pages that turned out not to be product pages took 7 s and 13.5 s, so the shopper was told to try again about a link that was about to say what was wrong with it. `LOOKUP_DEADLINE_MS` is 20 s, argued in `lib/deadline.ts`, and only a person who pasted an address ever waits that long. *The grid picture is `cleaned_url`.* A listing carries a cut-out made for grids beside the raw `url`; the module prefers `cleaned_url` and falls back to `url`, so a tile shows the product on white rather than a lifestyle photograph with the product in a corner. |
