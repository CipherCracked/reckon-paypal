# ITD 39 — Our Route Makes the Agreement; the Button Only Approves It

| ITD 39 — *"Let the SDK's callback call our existing route and return its id, and let the receipt verify approval by reading PayPal again."* |  |
| :---- | :---- |
| **THE PROBLEM** | IPD 48 puts PayPal's one-time button and its subscription button on the consent screen. Both take a callback that returns an id — `createOrder: () => Promise<{ orderId: string }>`, `createSubscription: () => Promise<{ subscriptionId: string }>` — and a static-id alternative. Everything that decides whether money is right already lives on the server: `computeCommitment` produces the amount the figures printed; `/api/paypal/orders` and `/api/paypal/subscriptions` resolve the product, refuse a listing whose term nobody read, refuse a shape that disagrees with the route (an order route asked for a subscription, and the reverse), pass the amount and the cycle count to PayPal, and log the amount-mismatch failure, which is the check this product exists to enforce. The subscription route also calls `ensurePlan` under a deterministic id, `P-DEMO-<SLUG>`, so the plan is created once and reused. The browser also needs a client id, and the repo has never sent anything to the browser except rendered figures and a slug. Two questions follow: what may the button's callback do, and what is allowed to happen *after* the shopper approves? |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **The callbacks call the existing routes — `/api/paypal/orders` and `/api/paypal/subscriptions` — with the slug, and return the id each already answers with. The server component passes only `PAYPAL_CLIENT_ID` to the provider. After approval the shopper is sent to the receipt, which re-reads the agreement from PayPal and states what PayPal reports, so a subscription that is not yet settled says so.** <br> 2. Create the order or subscription when the button is rendered, so the press only approves an object that already exists. <br> 3. Create the subscription in the browser from a `plan_id` handed to the page. <br> 4. Pass a static `orderId` or `subscriptionId` created on the server before render. <br> 5. Verify approval only for one-time purchases, and let a subscription go straight to the receipt on `onApprove`. <br> 6. Capture or activate from the browser: have `onApprove` call PayPal directly, or trust `onApprove` as the payment. |
| **REASONING** | The deciding factor is **where the amount agreement lives**. Every route in this repo that can take money resolves the product, computes the figure and refuses to send PayPal anything else; the amount-mismatch failure is logged, not swallowed, because two figures for one payment is the failure the whole product is built against. Option 3 hands the browser a plan id, and a plan id is a promise about a price and a cycle count — the browser would be choosing which promise to approve. Option 1 is the smallest change that keeps that check on the server: the route already returns `subscriptionId` and `orderId`, and the SDK's documented shape is exactly `{ subscriptionId }`, so nothing needs reshaping. <br><br> Options 2 and 4 both create an object **before the shopper asks for one**. A subscription created at render is an `APPROVAL_PENDING` agreement in PayPal's ledger for every visitor who looks at the screen, including those who leave without pressing. It costs the merchant a record per look, and it makes *nothing has been charged* a sentence about a plan that nonetheless exists. Creating nothing until the press keeps the screen a screen. <br><br> The client id is public by design — it identifies the app, and PayPal's own guides put it in the page — while the secret is what signs requests, and it has never left the server. Option 1 passes only the id, as a prop from the server component, so there is no new route and no new surface; a test asserts the rendered output contains the id and not the secret, and that assertion is cheap because the boundary is a single prop. <br><br> Approval is not settlement, and the difference is already built. `isSettled` is what the receipt uses to decide whether to show figures at all, and `CANCELLED` is settled while `APPROVAL_PENDING` is not — so a subscription approved a second ago and not yet activated lands on *Nothing has been taken yet* rather than on a record of a payment that has not happened. Option 5 would skip that check for the shape most likely to be unready, which inverts the product's own rule: the longer the commitment, the more careful the screen. The receipt is therefore the verification, and its existing sentences are the whole of the post-approval story. <br><br> Option 6 puts capture in the browser, which the current code deliberately does not do: capture is a server call with a credential, and `ALREADY_CAPTURED`, `PENDING` and `COMPLETED` are three different sentences the server has already been taught to distinguish. <br><br> The return URLs stay. They are what the fallback link (IPD 50) uses, and the routes already build them from our own origin rather than from the request, so nothing about them changes. |
| **TRADEOFFS** | The in-page press now costs two round-trips to our own server — resolve the product, then create the object — and the SDK holds its own state while it waits. On a slow sandbox that can read as a button that did nothing, so the control's disabled state has to be honest about it. <br><br> The route is re-entered on every press, and a shopper who presses twice after an error creates a second object. Nothing is captured for the first, and it is inert at PayPal, but the merchant's ledger accumulates them. The alternative — holding a created object across presses in the client — is state on the money screen that can go stale against the terms. <br><br> The subscription's activation is not waited on. A shopper approved a moment ago sees *Nothing has been taken yet* until PayPal reports the agreement settled, which is true and is also the least satisfying screen in the product at the moment of success. <br><br> The client id becomes part of the page, which is normal, and it is the first PayPal value the browser has ever been given. It is not a secret; it is also not nothing. |
| **NOTES** | `components/ConsentScreen.tsx` — the `pay()` branch that chooses between the two routes moves into the render, because the button must exist before it is pressed; the callbacks keep the same requests and the same failure sentences. The primary button and the `approve` state stay for the fallback path. <br><br> `app/consent/[orderId]/page.tsx` — a server component already; it passes `process.env.PAYPAL_CLIENT_ID` into the screen as `clientId`. Never `PAYPAL_CLIENT_SECRET`, which stays where it is read, in `lib/paypal/client.ts`. <br><br> No new route. `/api/paypal/orders` and `/api/paypal/subscriptions` are called unchanged, and their refusals — a product that cannot be charged, a shape that disagrees, a missing key — surface as the control's error state rather than as a navigation. <br><br> `onApprove` for a one-time purchase still needs the capture: the SDK reports approval, and `/api/paypal/orders/{id}/capture` is what makes the money move. Its three answers keep their three sentences. For a subscription there is no capture; the route to the receipt is the whole of it. <br><br> The receipt URL is built from the id PayPal or our route returned, with `slug` carried through so the record keeps the product's name. |
