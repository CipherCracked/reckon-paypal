# ITD 40 — The Script Is Loaded Behind the Screen, and the Untestable Surface Is One Component

| ITD 40 — *"Put PayPal's provider and button inside one client component, load it after the figures, and let the screen keep every decision that is ours."* |  |
| :---- | :---- |
| **THE PROBLEM** | `@paypal/react-paypal-js` is a client library: it loads PayPal's script into the page, renders the button into a container it owns, and reports the script's state through `usePayPal()`. Verified on 2026-11-12 against version **10.6.1** (peer React `^16.8 \|\| ^17 \|\| ^18 \|\| ^19`, so this project's React 19 is in range): the provider is `PayPalProvider`, taking `clientId` and a `components` array — `["paypal-payments"]` by default, `"paypal-subscriptions"` required for the subscription button; the buttons are `PayPalOneTimePaymentButton` and `PayPalSubscriptionButton` from the package's `sdk-v6` entry point; loading is read with `usePayPal()` as `INSTANCE_LOADING_STATE.PENDING \| REJECTED` plus an `error`. The consent screen is the app's most-tested component — its states, its sentences, the capture path and the fallback all have tests — and this repository's suite runs in **jsdom**, where PayPal's script cannot execute. So the question is not whether to use the library but **where its boundary sits**, because everything inside it is unprovable here and everything outside it is the product's own behaviour. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **One client component — `PayPalButton` — owns `PayPalProvider` and the button. It is imported by the consent screen through `next/dynamic` with `ssr: false`, given the shape, the slug and the client id as props, and told what to call when the shopper pays and what to render when the script cannot load. Every decision the product makes — which route, which sentence, which state — stays in the screen; the suite mocks this one module and asserts the screen's wiring around it.** <br> 2. Put the provider and the buttons directly in `ConsentScreen`, which is already a client component. <br> 3. Put the provider in the app shell so every screen can render a PayPal control. <br> 4. Render the button on the server and hydrate it. <br> 5. Add a browser test runner (Playwright) and drive the real button end to end. <br> 6. Skip the provider entirely and load PayPal's raw script by hand. |
| **REASONING** | The deciding factor is **how much of the product becomes unobservable**. Option 2 is the smallest edit and the largest cost: `ConsentScreen` would import the SDK at module scope, so every one of its existing tests would need the SDK mocked before it could render a figure — the most-tested screen becomes the screen whose tests assert a mock. Option 1 leaves the boundary at one module with four props. The screen keeps its own state machine, its own sentences and its own tests; the suite replaces the button with a stub and can assert exactly what the screen passed it and how it reacts to *paid*, *cancelled* and *unavailable*. <br><br> Option 3 loads PayPal's script on every page for the sake of one screen: a receipt, a shop, a document reader, and the front door would each carry a third-party request they never use. Option 4 is not available — PayPal's button needs `window`, and the whole point of the provider is a client-side script. <br><br> Option 5 is the honest way to test the real control and the wrong one for these hours: it adds a browser, a runner and a CI story to a repository with one suite and a deadline today. The verification it would buy is bought instead by a live pass, recorded in the run notes — and the fact that this is a compromise is stated in Tradeoffs rather than dressed up. <br><br> Option 6 gives up the provider's loading and error reporting, which IPD 50 depends on for its fallback, and hand-rolls a script tag whose failure the product would then have to detect itself. <br><br> Dynamic import with `ssr: false` is what makes the boundary real: the SDK is not in the server bundle, the consent screen's first paint does not wait for it, and a failure inside it cannot take the page down. The component then reads `usePayPal()` to decide between the button, the *Preparing PayPal's button* sentence, and the fallback — and the fallback is not new code: it calls the same `pay()` the link path already uses, so the existing `approve` state, the existing notice and the existing return handling are what the shopper gets when PayPal's script does not arrive. |
| **TRADEOFFS** | Everything about the button's own rendering — its size, its label, whether the click registers, whether PayPal's window opens — is invisible to the suite. The tests can prove the screen passed the right route and the right shape; they cannot prove the button works, and only the live pass can. <br><br> The component is a stub in every test, so a mistake inside it — a wrong prop name, a missed `disabled` while creating — fails nothing in CI. Keeping it to four props and roughly a hundred lines is the mitigation, not a guarantee. <br><br> `ssr: false` means the button appears after hydration. On a slow connection the screen is readable and unpayable for a moment, which is what the *Preparing PayPal's button* sentence is for and also a state the shopper can see for longer than they would like. <br><br> One more client boundary and one more dynamically imported chunk, on a screen that was already the heaviest in the app. The chunk is small; the third-party script it fetches is not, and it is fetched only when the screen mounts, never on the servers that render it. |
| **NOTES** | `components/PayPalButton.tsx` — new, client. Owns `PayPalProvider` (`clientId`, `components` chosen by shape, `pageType="checkout"`), renders `PayPalOneTimePaymentButton` or `PayPalSubscriptionButton`, and reads `usePayPal()` for `PENDING` and `REJECTED`. Props: `shape`, `clientId`, `createOrder`/`createSubscription` (or a single `create` callback plus the shape), `onApproved`, `onCancelled`, `onFailed`, `onUnavailable`. <br><br> `components/ConsentScreen.tsx` — imports it with `next/dynamic` and `ssr: false`; on `onUnavailable` it sets the existing `approve` state by calling `pay()`, so the fallback is today's path rather than a second implementation. The existing primary button, its `approve` notice and the `returning` capture effect are untouched and remain the fallback's machinery. <br><br> `app/consent/[orderId]/page.tsx` — passes `clientId` (ITD 39). A test asserts the secret's value cannot appear in the rendered output; the prop boundary has no way to carry it. <br><br> `tests/consent-page.test.tsx` — the button module is mocked; the tests assert that the screen renders it with the resolved shape and the slug, and that each of its outcomes produces the sentence it should. The withdrawal of the SDK's own behaviour from the suite is recorded here rather than left to be discovered. <br><br> Live verification, recorded in `todo.md` when it runs: the script blocked at the network layer shows the fallback sentence and the link still works; a slow script shows the preparing sentence with the figures above it; a real subscription approval lands on the receipt and says what PayPal reports. |
