# ITD 35 — The Reading Is Kept, and Shown While It Lands

| ITD 35 — *"Keep one whole-listing reading in the memory the exit reader already uses, keyed by the listing's own words, and stream the product page's commitment panel so the catalogue's answer appears before the model's."* |  |
| :---- | :---- |
| **THE PROBLEM** | A reading costs roughly 47 seconds on the current free endpoint, and after ITD 34 it stands between a shopper and every figure on a product page. Three things already soften that cost, and all three were built when only four listings needed reading: the reading is remembered for ten minutes on `globalThis` (`lib/commitment/published-exit.ts:81–93`), readers arriving mid-read join the same promise (`:139–160`), and the texts that can be predicted are read at server start (`instrumentation.ts` → `lib/commitment/warm.ts`). <br><br> None of the three scales to *any listing*. A catalogue product a visitor opens for the first time has no warmed reading, and the page currently resolves everything in one await: title, image, price and figures arrive together or not at all. If the reading joins that await, the catalogue's 300-millisecond answer waits 47 seconds behind a model (IPD 39). If it does not, the screen has to describe a state it has no data for yet — the reading is in flight, and nothing on the page says so. <br><br> The cache's existing guarantees are load-bearing and must survive the change. It is keyed by text, so a merchant's edit is a different key and an edited listing can never be quoted from the old reading. Failures are deliberately not remembered, because a timeout is a fact about one attempt (`:174–179`). Past its ten minutes a stale entry is served while a refresh runs behind the reader, because an unchanged sentence does not become wrong by aging (`:113–124`). <br><br> The last thing this must not become is an empty screen: the product page is the first place in the product where the model does visible work, and a spinner would hide the one thing worth showing. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **Extend the existing cache to hold the whole listing reading, keyed by the text exactly as the exit reading is; the product page renders the listing immediately and streams the commitment panel inside a Suspense boundary that waits up to the answer ceiling; every other caller reads only what is remembered.** <br> 2. Key the cache by product id, one entry per listing. <br> 3. Resolve everything in one await and give the whole page the answer budget. <br> 4. Render the page, then have the client poll a route until the reading lands. |
| **REASONING** | **Text is the right key because text is what was read.** The term is a fact about a title and a description, not about an id. Keying by id would serve a stale term after an edit until the TTL expired — the exact failure `termIsStated` exists to prevent for the curated map (`lib/market/subscriptions.ts:43–56`) — and would need a text comparison to detect it, which is the text key arriving by another route. Keying by text also means the same product listed twice (`zHpJR9Q` and `zm8tw4C`) is read once when the words match. <br><br> **Streaming is the only option that shows both answers at their own speed.** The product page is already a server component and the catalogue answer is already in hand when the model is called; a Suspense boundary renders the first part immediately and the commitment when the promise settles, with no client state, no second route and no polling interval. It also degrades honestly without JavaScript: the fallback is server-rendered HTML that states what is being read. Option 4 buys the same result with a route, a client component and a state machine the page does not otherwise need. Option 3 hides the catalogue behind the model and is refused by IPD 39. Option 2 is refused for the staleness reason above. <br><br> **The budgets are per caller, so the sharing is per promise.** A caller with the 3-second render budget resolves to its fallback while the underlying reading continues and fills the cache — `withBudget` already refuses to cancel expensive work (`lib/deadline.ts`), and that is what makes a cold listing's second render instant even if its first gave up. The product page passes no early fallback: it is the page whose subject is the reading, so it gets the answer ceiling (`MODEL_ANSWER_DEADLINE_MS`) rather than the render one. <br><br> **The warm-up stays a sample and says so.** Four fixture listings and the file texts are read at start-up, in sequence because a free endpoint serialises (`lib/commitment/warm.ts:44–49`). No amount of warming covers a catalogue; the warm-up exists to keep the front door and the demo's first screens instant, not to pretend the problem is solved. |
| **TRADEOFFS** | A streamed page means the button that starts agreeing arrives after the content around it. If the reading fails or is slow, the page a shopper is looking at has no action in it for most of a minute, and the layout must not jump when it arrives. <br><br> The fallback is the most-read sentence on a cold listing. It has to say what is happening, name whose words are being read, and survive being screenshotted — a skeleton that looks like a loading state wastes the only moment the product shows the model at work. <br><br> A shared promise means one slow reading holds one slot per text, and the three-minute ceiling (`published-exit.ts:136`) exists because a promise that never settles would otherwise hold it for the life of the process. Any new failure mode that leaves a promise pending inherits that risk. <br><br> Nothing is persisted. A restart re-reads the fixtures and loses every other listing's reading; a deployed serverless instance that is recycled has the same cost. That is acceptable for a ten-minute cache and is why the cache lives on `globalThis` rather than in a module — Next compiles the start-up hook and the pages into separate graphs (`:77–80`). |
| **NOTES** | **This is not the `loading.tsx` case.** ITD 32 refused a route-level boundary because a streamed `redirect()` was committed as a `200` with a truncated body. This is a Suspense boundary inside a page that renders rather than redirects, with no route-level `loading.tsx` — the redirect path (`app/shop/page.tsx`, a pasted link) is untouched. <br><br> The in-flight promise and the cached finding are the same objects the exit reader uses today; the decision is to widen the payload from `ExitFinding` to a listing reading, not to add a second cache. That keeps one TTL, one ceiling, one single-flight rule and one place where a failure is decided not to be remembered. <br><br> The reading's span travels with it, so the streamed panel can print the merchant's sentence under the figure the moment it lands (IPD 40, ITD 33). <br><br> What the page does when the ceiling expires is the fourth state in IPD 40: a sentence about us, a way to try again, and no button. The reading is not cancelled, so a retry usually finds it finished. |
