# ITD 27 — The Layout Belongs to the Card

| ITD 27 — *"Use a container query on the commitment card and a flex `order` on the entry pair, so the layout answers to the space the card actually has rather than to the width of the window."* |  |
| :---- | :---- |
| **THE PROBLEM** | Once the figures had a hierarchy (ITD 26) they had notes under them — an arithmetic line and, for the quoted figure, the seller's sentence. Two columns of those notes need about 30rem to sit without colliding. The first version decided that with a viewport media query at 44rem, which is the wrong input: the same card is half of a 1440-wide page and all of a 390-wide phone, so a 900px window rendered a 430px card in one column while a 700px window rendered a 430px card that believed it was wide. The notes wrapped to one word a line. <br><br> The entry has the same shape of problem from the other side. It pairs the seller's words with the figures, and the order the two panels should be *seen* in changes with width: side by side, words first as they are in the markup; stacked on a phone, the figures first, because a person scanning a phone wants the numbers before the paragraph that produced them. The markup cannot serve both orders, and duplicating the pair to hide one copy would render the figures twice on every screen. <br><br> A third defect surfaced while testing the fix: the pair's columns were grid cells aligned to their content, and switching the container to a flex column with the default `align-items: start` shrank each panel to the width of its longest line, so the phone layout collapsed to a few words per line. |
| **OPTIONS CONSIDERED (Decision in bold)** | 1. **The card is a size container (`container-type: inline-size`) and decides its own one-vs-two-column figure layout at `@container (max-width: 30rem)`. The entry pair is a grid at two columns and, below 44rem, a flex column whose two children carry `order: 2` and `order: 1` — the words still first in the DOM, the figures first on screen — with `align-items: stretch` so both panels keep the full width.** <br> 2. Keep viewport media queries and tune the breakpoints until nothing collided. <br> 3. Measure the card in JavaScript with a `ResizeObserver` and set a class. <br> 4. Render the pair figures-first in the DOM and reverse the order on wide screens. |
| **REASONING** | The deciding factor is **whose width the question is about**. "Can two columns of notes sit here without colliding" is a question about the card, so the card is what should answer it; a media query answers a question about the window and is only ever right by coincidence. The container query is not a breakpoint to tune — it is the component carrying its own layout, which is the same reason `FigureGrid` renders the figures rather than each screen doing it (ITD 25): the card appears in four places and all four should behave the same at the same width. <br><br> The second factor is **what the DOM order is for**. The seller's words come first in the markup because that is the evidence and the sequence the product argues in; on a phone the figures come first because that is what a person came to see. `order` gives the phone the visual sequence without moving anything out of the reading order, and both panels stay complete and focusable — nothing is hidden, so nothing is lost to a screen reader. Option 4 inverts the same mistake: putting the figures first in the DOM to please the phone makes the wide layout argue for the numbers before showing what they were worked out from. <br><br> Option 2 is rejected because the notes' collision depends on the card's width, which no viewport breakpoint can express once the page has two columns; it would need a different value for every page that hosts the card. Option 3 is rejected because it buys the same behaviour with a JavaScript dependency, a flash of the wrong layout before the observer fires, and no server-rendered answer for the first paint. <br><br> `align-items: stretch` is part of the decision rather than a bug fix: a flex column of panels means full-width panels, and grid's content-alignment default was inherited into a context where it reads as a squeezed page. |
| **TRADEOFFS** | On a phone the visual order and the tab order disagree by one panel: a keyboard user tabs into *Check this commitment* — which lives under the seller's words — before reaching the figures above it. The panels are short and the link is the only focusable element in either, so the cost is one early tab stop rather than a trapped focus; the alternative reorders the evidence for everyone. <br><br> `container-type: inline-size` makes the card a size container, so it cannot be sized *by* its contents in the inline direction; the card's width now always comes from its parent, which is true of every current use but is a constraint the next one inherits. <br><br> The figure rules between stacked rows are set inside the container query, so they are two sets of CSS for one grid; the card's compact variant keeps its own list layout and does not participate. <br><br> Neither rule has a test. Layout is verified by screenshot at 1440 and 390, which is a manual step nothing in the suite will tell you to repeat. |
| **NOTES** | The same pass set the page's rhythm: one padding on `.page`, a 38rem measure on the lede, and a `text-wrap: balance` heading. Those are values, not decisions — they exist so that eight routes do not each choose their own again. <br><br> `.front-doors` was already `auto-fit`/`minmax(17rem, 1fr)`, which is the same principle applied earlier; it needed no change. |
